## 1. 文档概述

### 1.1 目的
本文档描述 CubeShop V1.0 MVP 的整体技术架构、分层设计、核心模块划分、认证权限方案、数据流与部署方案，作为开发、联调与后续迭代的技术基线。

### 1.2 设计原则
| 原则 | 说明 |
|------|------|
| **单体优先** | V1.0 采用单体应用，降低复杂度，快速交付可上线版本 |
| **清晰分层** | 前后端分离，后端按领域分层，便于后续拆分 |
| **事务一致性** | 库存、订单、支付等关键路径使用数据库事务保证强一致 |
| **权限可扩展** | 功能权限（菜单/按钮）与业务权限分离，支持后续细化 |
| **可替换基础设施** | Redis 可选，无 Redis 时可用 PostgreSQL 承担缓存/队列 |
| **高信息密度 UI** | 管理端对齐企业后台风格，紧凑、高效 |

### 1.3 系统边界
- **系统内**：用户端（买家）、管理端（运营/超管）、API 服务、定时任务
- **系统外**：支付渠道（微信/支付宝）、短信/邮件服务（可选）、对象存储（图片，后续）

**层级说明**：
- **客户端层**：用户端与管理端，通过 HTTP/JSON 访问后端。
- **API 网关 / Nginx**：统一入口，负责反向代理、静态资源、SSL、基础限流。
- **Laravel 应用层**：业务核心，包含中间件、业务 Service、领域 Model。
- **公共服务层（Common）**：跨业务模块复用的基础能力（订单号生成、统一响应、文件上传、导出、日志、缓存封装、分布式锁等），供前后端业务代码共同调用，避免重复实现。
- **基础设施层（Infrastructure）**：PostgreSQL、Redis、对象存储、Excel 引擎、Scheduler、Queue Worker、外部支付/短信等真实运行时依赖。

## 4. 分层设计

### 4.1 后端分层

| 层 | 职责 | 典型目录/类 |
|----|------|-------------|
| **Controller** | 接收请求、参数校验、调用 Service、返回统一响应 | `app/Http/Controllers/...` |
| **Request** | 表单/查询参数验证 | `app/Http/Requests/...` |
| **Service（业务服务）** | 业务编排、事务控制、调用多个 Model/Repository | `app/Services/OrderService.php` 等 |
| **Model** | 数据映射、关联、简单查询 | `app/Models/...` |
| **Repository**（可选） | 复杂查询封装，降低 Service 与 Eloquent 耦合 | `app/Repositories/...` |
| **公共服务层（Common）** | 跨模块可复用的基础能力 | 见下方详细说明 |
| **Job / Command** | 异步任务、定时任务（超时取消订单等） | `app/Jobs/`、`app/Console/Commands/` |
| **Middleware** | 认证、权限、限流、日志 | `app/Http/Middleware/` |
| **基础设施层** | 数据库、缓存、存储、外部 SDK 等 | 配置与驱动层 |

**调用约定**：
- Controller **不写** 业务逻辑与事务
- Service 负责 `DB::transaction()` 包裹库存、订单、支付相关操作
- 跨模块调用优先通过 Service，避免 Model 互相深度耦合
- 业务 Service 通过 **公共服务层** 调用订单号生成、文件上传、导出、日志等，不直接依赖基础设施细节

#### 4.1.1 公共服务层（Common Services）详细说明

公共服务层封装前后端业务都可能用到的基础能力，统一实现、统一调用，避免各业务模块重复造轮子。

| 公共服务 | 职责 | 典型实现建议 |
|----------|------|--------------|
| **订单号生成服务** | 生成全局唯一、可读的订单号/支付单号 | 雪花算法 / 日期+序列 / Redis INCR |
| **ID 生成服务** | 业务主键、流水号生成 | 雪花算法或数据库序列 |
| **统一响应封装** | 标准化 API 返回结构（code/message/data） | Response Helper / Middleware |
| **操作日志服务** | 记录关键写操作（人、时间、动作、目标） | `OperationLogService` |
| **文件上传服务** | 图片/附件上传、校验、压缩、存储路径返回 | 对接 Laravel Storage |
| **导出服务** | Excel/CSV 导出封装 | 基于 maatwebsite/excel |
| **缓存封装** | 统一 get/set/forget、缓存键规范 | Cache Facade 二次封装 |
| **锁与限流工具** | 分布式锁、接口限流 | Redis 锁 / RateLimiter |
| **配置读取服务** | 读取 `system_configs` 等业务配置 | ConfigService |
| **通知服务**（可选） | 短信、邮件发送封装 | 对接外部网关 |

**目录建议**：
```
app/Services/Common/
  ├── OrderNoGenerator.php
  ├── IdGenerator.php
  ├── OperationLogService.php
  ├── FileUploadService.php
  ├── ExportService.php
  ├── CacheService.php
  └── ConfigService.php
```

#### 4.1.2 基础设施层说明

基础设施层是真正的运行时依赖，业务代码与公共服务通过接口/驱动访问，不直接硬编码实现细节。

| 组件 | 用途 | 说明 |
|------|------|------|
| **PostgreSQL 14+** | 主业务数据存储 + 事务 | 核心强一致数据 |
| **Redis**（可选） | 缓存、队列、限流、分布式锁 | 无 Redis 时可用 PostgreSQL 替代 |
| **对象存储** | 商品图片、附件 | Laravel Storage（本地或 OSS/S3） |
| **Excel 引擎** | 列表与报表导出 | maatwebsite/excel |
| **Scheduler / Cron** | 定时任务（订单超时取消等） | Laravel Scheduler |
| **Queue Worker** | 异步任务消费 | `php artisan queue:work` |
| **支付渠道 SDK** | 微信/支付宝支付与退款 | 官方或第三方 SDK |
| **短信/邮件网关** | 通知（可选） | 第三方服务 |

### 4.2 前端分层（管理端）

| 层 | 职责 | 约定 |
|----|------|------|
| **Views / Pages** | 页面级组件 | `src/views/` |
| **Components** | UI 基础组件 + 业务组件 | `components/ui`（shadcn）、`components/biz` |
| **API** | 按领域拆分请求 | `src/api/product.ts`、`order.ts` 等 |
| **Stores** | 全局状态（用户、权限、字典） | Pinia `src/stores/` |
| **Router** | 路由 + 权限守卫 | `src/router/`，`meta` 中声明权限码 |
| **Utils** | 工具、权限指令 | `src/utils/`、`directives/` |

**路径别名**：`@/` → `src/`

## 5. 核心业务模块划分

### 5.1 模块一览

| 模块 | 职责 | 主要实体/表 |
|------|------|-------------|
| **系统与权限** | 用户、角色、权限、菜单、操作日志 | `sys_user`、`roles`、`permissions`、`sys_operation_log` |
| **商品** | 分类、商品、SKU、上下架、图片 | `categories`、`products`、`product_skus` |
| **库存** | 库存数量、锁定、流水、预警 | `inventories`、`inventory_logs` |
| **购物车** | 用户购物车项 | `carts`、`cart_items` |
| **订单** | 下单、状态流转、快照、取消、超时 | `orders`、`order_items` |
| **支付** | 支付请求、回调、退款、日志 | `payments`、`payment_logs` |
| **售后** | 退款申请与处理 | `refunds` |
| **配置** | 运费规则、超时时间、库存预警阈值 | `system_configs` |

### 5.2 关键业务闭环（事务边界）

#### 5.2.1 下单（创建订单）
```
OrderService::createOrder()
  └─ DB::transaction {
       1. 校验购物车商品有效性与库存
       2. 锁定/扣减库存（或预占）
       3. 写入 inventory_logs
       4. 创建 orders + order_items（商品快照）
       5. 清空/更新购物车
     }
```

#### 5.2.2 支付成功回调
```
PaymentService::handleCallback()
  └─ DB::transaction {
       1. 验签 + 幂等校验（防重复）
       2. 更新 orders 状态 → 已支付
       3. 写入 payments / payment_logs
       4. （如有预占）确认库存扣减
     }
```

#### 5.2.3 取消订单 / 超时取消
```
OrderService::cancelOrder()
  └─ DB::transaction {
       1. 校验状态允许取消
       2. 更新订单状态 → 已取消
       3. 释放库存
       4. 写入 inventory_logs
     }
```

#### 5.2.4 发货
```
OrderService::shipOrder()
  └─ 更新订单状态 → 已发货 + 操作日志
```

#### 5.2.5 退款处理
```
RefundService::approve()
  └─ DB::transaction {
       1. 调用支付渠道退款（或标记人工退款）
       2. 更新订单/退款状态
       3. 视业务决定是否回滚库存
     }
```

## 6. 认证与权限架构

### 6.1 认证流程（Laravel Sanctum）

```
1. 用户提交用户名/密码
2. 校验 sys_user（密码哈希）
3. Sanctum 颁发 Token（返回前端）
4. 后续请求 Header：Authorization: Bearer {token}
5. 中间件 auth:sanctum 解析用户
```

- 用户主数据使用本系统 `sys_user` 表，不依赖外部 Identity Provider（V1.0）
- 支持普通用户、运营管理员、超级管理员角色区分

### 6.2 权限模型

采用 **spatie/laravel-permission**：

| 概念 | 说明 |
|------|------|
| Role | 角色（如：超级管理员、运营、客服） |
| Permission | 权限码（如：`product.create`、`order.ship`、`order.refund`） |
| 分配关系 | 用户 ↔ 角色 ↔ 权限 |

**前端配合**：
- 路由 `meta.permission` 声明所需权限
- 路由守卫根据用户权限过滤可访问菜单
- 按钮级：自定义指令或组件根据权限码显隐

**后端配合**：
- 写操作接口使用 `can:permission_code` 或中间件校验
- 超级管理员可绕过或拥有全部权限

### 6.3 操作日志
关键写操作（商品变更、订单发货、退款、权限变更）写入 `sys_operation_log`，记录：操作人、时间、模块、动作、目标 ID、IP 等。

## 7. 数据架构要点

### 7.1 数据库选型
- **主库**：PostgreSQL 14+
- 支持事务、JSON 字段（规格、快照）、可靠并发控制
- 建议为订单号、用户 ID、商品 ID、状态字段建立合适索引

### 7.2 核心数据设计原则
| 原则 | 实践 |
|------|------|
| 商品快照 | `order_items` 保存下单时的标题、价格、规格，避免后续改价影响历史 |
| 库存流水 | 所有库存变更写 `inventory_logs`，便于对账与排查 |
| 幂等 | 支付回调使用唯一业务单号 + 状态判断，防止重复入账 |
| 软删除 | 商品、用户等重要数据优先软删除 |
| 配置外置 | 运费、超时分钟数、库存预警阈值存 `system_configs` |

### 7.3 缓存策略（Redis 或 PostgreSQL 替代）
| 场景 | 策略 |
|------|------|
| 热点商品详情 | 短时缓存，更新时失效 |
| 用户权限 | 登录后缓存权限列表 |
| 限流 | 登录、下单接口限流 |
| 队列 | 异步导出、可选通知任务 |

无 Redis 时：使用 PostgreSQL 的 `cache` 表或 Laravel 的 database 驱动作为缓存/队列后端。

## 8. API 设计原则

### 8.1 风格
- RESTful 风格为主
- 统一响应结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": { ... }
}
```

- 错误码分层：业务错误（可展示给用户）、系统错误（记录日志）

### 8.2 接口分组建议
| 前缀 | 说明 |
|------|------|
| `/api/auth/*` | 登录、注册、重置密码、退出 |
| `/api/user/*` | 个人中心、地址 |
| `/api/products/*` | 前台商品列表、详情、搜索 |
| `/api/cart/*` | 购物车 |
| `/api/orders/*` | 下单、取消、列表、详情、退款申请 |
| `/api/payments/*` | 支付发起、回调（回调需单独验签） |
| `/api/admin/*` | 后台管理接口（商品、订单、分类、权限等） |

### 8.3 安全要点
- 支付回调必须验签 + 幂等
- 写接口 CSRF/Token 保护（Sanctum）
- 敏感操作二次校验或权限码强校验
- 接口限流（登录、下单）

- **技术**：Vue 3 + TypeScript + Vite + Pinia + Vue Router

- 动态路由：根据用户权限生成可访问菜单
- 按钮权限：指令 `v-permission="'order.ship'"` 控制显隐

## 15. 总结

CubeShop V1.0 采用 **Laravel 单体 + Vue 3 管理端 + PostgreSQL** 的经典可快速交付架构：

- **后端**：清晰的 Controller → 业务 Service → Model 分层，关键路径用事务保证库存与订单一致性
- **公共服务层**：订单号生成、文件上传、导出、操作日志、缓存封装等跨模块基础能力统一提供
- **认证权限**：Sanctum + spatie/laravel-permission，支持菜单与按钮级控制
- **前端**：Tailwind + shadcn-vue 打造高信息密度企业后台
- **基础设施层**：PostgreSQL、Redis（可选）、对象存储、Excel 引擎、Scheduler、Queue Worker、支付渠道等

该架构在保证 V1.0 快速上线的同时，通过公共服务层与基础设施层的清晰划分，为后续模块扩展与适度拆分预留了良好边界。
