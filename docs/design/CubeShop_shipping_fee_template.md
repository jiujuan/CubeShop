商品物流运费的计算、后台设置与前端展示，是电商系统中的核心能力之一。结合当前项目文档（CubeShop v1.0/v2.0 与 TiShop/SaaS 体系），下面按问题逐一分析。

---

## 1. 运费根据什么进行计算？

电商系统中，运费计算通常支持多种规则，从简单到复杂逐步演进。项目现状与常见模式如下：

### 当前项目已有设计

| 项目              | 计算方式                       | 说明                                                         |
| ----------------- | ------------------------------ | ------------------------------------------------------------ |
| **CubeShop v1.0** | 固定运费 或 按地区简单规则     | 系统配置 `order.freight_default = 10.00`，订单表有 `freight_amount` 字段 |
| **CubeShop v2.0** | 运费模板按地区（系统配置增强） | PRD 明确提到“运费模板按地区”                                 |
| **TiShop / SaaS** | 按地区 + 重量模板              | 商品有 `weight` 字段用于运费计算；Store 关联 `ShippingTemplate`；结算页支持“按地区/重量模板” |

### 行业常见计算维度（按复杂度排序）

1. **固定运费**  
   - 全站统一金额（如统一 10 元），或包邮。  
   - 最简单，适合初期或虚拟商品。

2. **按收货地区（省/市/区）**  
   - 最常用。  
   - 不同省份/城市设置不同首重/续重价格。  
   - 可细化到“偏远地区加价”或“指定地区包邮”。

3. **按商品重量 / 体积**  
   - 商品维护 `weight`（或体积），运费 = 首重费用 + 续重费用 × 续重数量。  
   - TiShop 已预留 `weight` 字段。

4. **按快递公司 / 配送方式**  
   - 用户可选“顺丰”“圆通”“京东快递”等，每种有独立价格表。  
   - 通常与“地区 + 重量”组合使用。

5. **按订单金额 / 件数门槛**  
   - 满 X 元包邮、满 N 件包邮。  
   - 常作为优惠规则叠加在运费模板之上。

6. **组合规则（推荐完整方案）**  
   - 运费模板 = 配送方式 + 地区分区 + 首重/续重（或按件）+ 包邮门槛。  
   - 一个商品可绑定某个运费模板，或继承店铺默认模板。

**结论**：运费**不是只按快递公司**，也**不是只按地点**，而是通常以「运费模板」为核心，综合「收货地区 + 重量/件数 + 配送方式 + 包邮规则」计算。快递公司更多是发货时选择的履约方式，而不是运费计算的唯一依据。

## 2. 在后台哪里可以设置？

### CubeShop（当前）

- **v1.0**：系统配置中心  
  - 配置项：`order.freight_default`  
  - 位置：后台「系统设置 / 配置中心」
- **v2.0**：增强为「运费模板按地区」  
  - 建议位置：后台「物流管理 / 运费模板」或「系统配置 → 运费规则」

### TiShop / 更完整的 SaaS 设计（推荐）

后台应有独立模块：

**路径建议**：商家后台 → **物流 / 配送设置 → 运费模板**

可配置内容：

| 配置项      | 说明                                |
| ----------- | ----------------------------------- |
| 模板名称    | 如「普通快递」「生鲜专线」          |
| 计费方式    | 按重量 / 按件数 / 固定运费          |
| 地区分区    | 默认运费 + 指定省份/城市特殊价格    |
| 首重 / 续重 | 首重 1kg 8 元，续重每 1kg 加 2 元等 |
| 包邮条件    | 满 99 元包邮、指定地区包邮          |
| 默认模板    | 店铺默认运费模板                    |
| 商品绑定    | 商品可单独指定模板，或继承店铺默认  |

发货环节（与运费计算分离）：
- 发货时选择**物流公司 + 填写运单号**（CubeShop v2.0 已规划物流公司对接）。
- 运费是下单时算好并写入订单的，发货只是履约。

## 3. 是根据快递公司、还是运送地点，还是其他？

**综合回答**：

- **主要依据**：收货地点（省市区）+ 商品重量/件数 + 运费模板规则。
- **快递公司**：通常不直接参与“运费金额计算”，而是：
  - 作为「配送方式」选项（用户可选，不同公司对应不同模板）。
  - 发货时由商家选择，用于填写运单号和后续轨迹查询。
- **其他常见因素**：
  - 商品是否设置了独立运费模板。
  - 是否满足包邮门槛（金额/件数）。
  - 优惠券是否可抵运费（需单独配置）。
  - 多仓库发货时，可能按最近仓或指定仓计算（当前项目未深入）。

简化理解：

```
运费金额 = f(收货地址, 商品重量/件数, 运费模板规则, 是否包邮)
配送方式/快递公司 = 用户选择 或 商家发货时指定（影响履约，不一定影响金额）
```

## 4. 前端怎么合理显示运费价格？

前端展示要兼顾**透明度**和**转化率**，避免用户在结算页才看到高额运费导致弃单。

### 推荐展示位置与方式

| 页面                    | 展示策略        | 说明                                                         |
| ----------------------- | --------------- | ------------------------------------------------------------ |
| **商品详情页**          | 运费预估        | “运费：¥10 起” 或 “满99元包邮”；用户登录且有默认地址时，可显示“配送至 XX，运费 ¥X” |
| **购物车页**            | 动态预估        | 根据当前选中商品 + 默认地址实时计算，显示“预计运费 ¥X”（未选地址时显示“运费待结算”） |
| **结算页（最关键）**    | 精确计算 + 明细 | 必须根据最终收货地址精确计算；金额明细中单独列出「运费」，支持切换地址后实时刷新 |
| **订单详情 / 支付成功** | 已确认金额      | 显示最终支付的运费金额，不可再变                             |

### 交互与体验细节建议

1. **地址驱动计算**  
   - 用户切换收货地址 → 立即重新计算运费并刷新应付总额。  
   - 无地址时：提示“请选择收货地址后查看运费”。

2. **金额明细清晰**  
   ```
   商品金额：¥198.00
   运费：¥10.00
   优惠券：-¥20.00
   ----------------------
   应付金额：¥188.00
   ```

3. **包邮提示**  
   - 差 X 元包邮时，可在购物车/结算页提示：“再买 ¥X 即可包邮”。

4. **多配送方式时**  
   - 若支持选择快递，展示选项卡或下拉：  
     - 普通快递 ¥8  
     - 顺丰速运 ¥15  
   - 默认选最低或推荐方式。

5. **预估与最终一致性**  
   - 详情页/购物车的预估应尽量接近最终结算金额，减少落差。  
   - 最终以结算页（有精确地址）为准，并写入订单 `freight_amount`。

6. **异常处理**  
   - 地址不在配送范围：明确提示“该地区暂不支持配送”。  
   - 计算失败：降级为默认运费或提示联系客服。

## 总结与落地建议

| 问题           | 结论                                                         |
| -------------- | ------------------------------------------------------------ |
| 根据什么计算？ | 以**运费模板**为核心，主要依据**收货地区 + 重量/件数**，可叠加包邮规则；快递公司更多是配送方式而非唯一计费依据 |
| 后台哪里设置？ | 商家后台「物流/配送设置 → 运费模板」；CubeShop 初期可用系统配置，后续升级为完整模板 |
| 前端如何显示？ | 详情页预估、购物车动态预估、结算页精确计算并展示明细，地址变更实时刷新 |

**当前项目状态**：
- CubeShop v1.0 已支持固定运费 + 简单地区规则，数据落在订单的 `freight_amount`。
- v2.0 和 TiShop 已规划更完善的「按地区/重量运费模板」，建议在后续迭代中把运费模板做成独立可配置模块，前后端统一用同一套计算逻辑，保证预估与实付一致。
