### T-002 [BE] 用户确认收货接口
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P1 / S0 前置 / 履约线 |
| 对应功能 | E02-A |
| 依赖 | T-001 |
| 关联 | T-005 前端按钮；T-015 评价依赖本任务产生的 `completed` 状态 |
| 预估 | 0.5 人天 |

**目标**：用户对「已发货」订单可主动确认收货，订单进入「已完成」，打通订单生命周期终点。

**实现步骤**
1. 路由 `POST /api/storefront/orders/{id}/confirm`（`auth:sanctum`），新增 `OrderController::confirm()`。
2. 校验链：订单存在 → 归属当前用户（否则 403）→ 当前状态为 `shipped`（否则按业务码拒绝）→ 走 `Order::canTransitionTo(completed)`。
3. 状态流转：`shipped → completed`，写 `completed_at`，写 `order_logs`（operator_type=user，operator_id=当前用户）。
4. 幂等处理：若已是 `completed`，直接返回成功（不重复写时间与日志），避免前端重复点击导致重复流水。
5. 返回订单简要信息（status、status_label、completed_at）供前端刷新。
6. 错误码约定：非本人订单 403；状态不允许 400 类业务码（复用 V1.0 业务异常体系，`BusinessException`）。

**测试要求**
- 单元：`Order::canTransitionTo()` 对 `shipped→completed` 允许、`pending_payment→completed` 拒绝。
- 接口/集成（Pest Feature）：① 发货后确认成功且 `completed_at` 非空；② 重复调用仍成功且只产生一条日志；③ 未发货（paid）调用被拒；④ 他人订单 403；⑤ 未登录 401；⑥ 订单不存在 404。
- 回归：取消订单、支付回调、发货接口用例不受影响。

**验收标准**：已发货订单确认后状态为 `completed`、`completed_at` 有值、时间轴出现完成节点；重复调用不产生重复数据；6 条接口用例全绿。

**证据**：`pest-T-002.txt`、`curl-T-002.md`（含成功与 4 类失败分支响应原文）、`commit-T-002.txt`

### T-003 [BE] 自动确认收货 Command 与配置项
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P1 / S0 前置 / 履约线 |

| 预估 | 0.5 人天 |

**目标**：发货后超过配置天数的订单自动确认收货，避免订单永久停留「已发货」。

**实现步骤**
1. `system_configs` 新增配置项 `order.auto_complete_days`（默认 7，可后台修改）；补种子数据与后台配置读写路径。
2. 新增 Command `orders:auto-complete`：查询 `status = shipped` 且 `shipped_at <= now() - N 天` 的订单，分批（每批 200）流转为 `completed`。
3. 写 `completed_at` + `order_logs`（operator_type=system，remark 标注「系统自动确认收货」）；`orders` 增加 `auto_completed` 标记字段（迁移，布尔，便于报表区分与争议排查）。
4. 注册调度：`app/Console/Kernel.php` 每小时执行一次；加 `withoutOverlapping()` 与日志输出（处理数量、耗时）。
5. 加 `--dry-run` 参数，便于上线前先看将要影响多少订单（灰度与统计用）。
6. 先在测试环境用 `--dry-run` 统计历史在途订单规模，形成结论写入上线注意事项。

**测试要求**
- 单元：时间判定边界（刚好 7 天 / 6 天 23 小时 / 8 天）分别处理正确。
- 接口/集成：构造 3 条 shipped 订单（超期 / 未超期 / 已成 completed），执行 Command 后仅超期订单被流转，且日志与 `auto_completed` 正确。
- 回归：手动确认（T-002）与自动确认不冲突；重复执行 Command 幂等（第二次处理数为 0）。
- 边界：订单量为 1000 条时单次执行时长与内存（分批验证）。

**验收标准**：超期订单被自动流转且可区分来源；重复执行无副作用；`--dry-run` 能准确预估影响范围；调度每小时生效。

**证据**：`pest-T-003.txt`、`sql-T-003.md`（执行前后状态对比）、`dryrun-T-003.txt`（历史订单影响统计）、`commit-T-003.txt`

| 项 | 内容 |
|----|------|

**目标**：订单列表支持分组 Tab 与多条件检索；用户可一键按历史订单再次加购。

**实现步骤**
1. `GET /orders` 扩展参数：`tab`（all/pending_payment/pending_ship/pending_receive/pending_review/after_sale）、`keyword`（订单号或收货人姓名/手机号，取 `address_snapshot` 字段）、`start`/`end`（下单时间区间）；保持 V1.0 的 `status` 参数向后兼容。
2. `tab` 与状态映射集中在一处常量（`Order::TAB_STATUS_MAP`），其中 `pending_review` = `completed` 且该订单无可评价行项目余额（关联 T-015 的 `reviews`，未完成时先按 `completed` 实现，T-015 完成后补精化）。

5. 返回结构：`{ added: N, skipped: [{product_id, title, reason}], cart_count }`，前端据此提示。
6. 列表响应补充字段：`items_preview`（前 3 个商品缩略图与名称）、`item_count`、`pay_amount`、`status_label`、可用于按钮控制的 `actions`（如能否取消/确认收货/评价/再次购买）。

**测试要求**
- 单元：`tab` 映射与状态过滤 SQL 正确；失效行判定（下架/无库存/删除）分别命中。
- 接口/集成：① 各 tab 返回数量正确；② keyword 命中订单号与收货人手机号；③ 时间区间边界（含当日）；④ rebuy 全成功；⑤ rebuy 混合失效场景 skipped 明细准确；⑥ 他人订单 rebuy 403。
- 回归：`GET /orders` 原有 `status` 参数与分页行为不变（既有用例不改断言仍通过）。

**验收标准**：6 类 tab 数据准确；检索组合可用；rebuy 后购物车数量与失效提示与实际一致；旧参数兼容。

### T-009 [BE] SKU 笛卡尔积生成与差异合并接口
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P1 / 信任线 |
| 对应功能 | E01 |
| 依赖 | T-007（接口依赖 T-008 的属性值数据） |
| 关联 | T-010 前端直接调用；T-012 迁移后的 SKU 也走此逻辑校验 |
| 预估 | 2.0 人天 |

**目标**：勾选规格值即自动生成完整 SKU 组合，编辑时保留已填的价格库存，只增删变化行 —— 这是属性体系的核心算法。

**实现步骤**
1. 新增 `ProductAttributeService::generateSkuMatrix(array $specsSelection): array`：入参形如 `[{attribute_id: 3, values: [11, 12]}, {attribute_id: 5, values: [21, 22, 23]}]`，输出笛卡尔积组合列表（含每个组合对应的 `specs` 快照 `{属性名: 值名}` 与维度签名）。
2. 组合上限保护：单商品 SKU 数超阈值（可配置，默认 200）时拒绝并提示，避免误选导致爆炸。
3. 差异合并 `mergeSkuMatrix(Product $product, array $matrix)`：
   - 以「维度签名」（属性名 + 值的确定性排序拼接）作为 SKU 身份标识（不用 id，避免顺序变化误判）；
   - 已存在签名 → 保留原 `price`、`stock`、`sku_code`、`status`；
   - 新签名 → 创建 SKU（库存 0、状态启用、价格默认为商品展示价）；`sku_code` 按「商品编码-序号」生成并保证唯一；
   - 消失签名 → 若该 SKU 有未完成订单引用（在途订单），不物理删除，改为 `status = 禁用` 并记录；无引用则软删除。
4. 事务保证：整个合并在数据库事务内完成；SKU 增删同步写库存记录（`inventories` / `inventory_logs`，复用 V1.0 库存服务，新增 SKU 建库存行，删除 SKU 库存清零并记流水）。
5. 批量设置辅助接口：`POST /admin/products/{id}/skus/batch-set`（按维度批量改价/改库存/改状态/启停，如「所有 M 码 +5 元」），返回受影响 SKU 数。
6. 商品保存接口 `POST/PUT /admin/products` 支持新的 `specs_selection` + `skus` 结构，同时保留旧 `skus[].specs` 结构入口（兼容 T-012 迁移前的调用方与测试）。

**测试要求**
- 单元（重点）：① 2 维度 3×4 = 12 组合、3 维度 2×2×2 = 8 组合；② 顺序变化不改变签名（幂等）；③ 合并时已存在 SKU 的价格库存保持；④ 新增与删除行识别正确；⑤ 超阈值拒绝；⑥ 在途订单引用的 SKU 不物理删除。
- 接口/集成：商品创建 → 生成 SKU → 修改规格组合 → 再次生成，最终 SKU 集合与价格库存断言；库存行与流水一致。
- 回归：现有商品 CRUD + SKU 相关用例全绿（尤其 `Admin/ProductController` 的 SKU 唯一约束跨库兼容用例）。

**验收标准**：SKU 行数 = 各维度值数量之积；重复生成不产生重复 SKU 且不丢失已填数据；在途订单引用 SKU 不被删除；库存流水与 SKU 变更一致；6 条单元用例全绿。

**证据**：`pest-T-009.txt`、`sql-T-009.md`（SKU 矩阵与库存流水核对）、`curl-T-009.md`（批量改价响应）、`commit-T-009.txt`
