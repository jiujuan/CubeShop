# 客户服务中心 三期（智能化与规模化）任务清单

**任务编号**：CS-301 ~ CS-310
**阶段目标**：把「人工兜底」升级为「机器人前置 + 人工高效协同」—— 在线即时会话、智能客服机器人、SLA 超时预警、负载均衡分配、服务质量报表与导出。
**预估**：18~24 人天
**开工前置**：**Gate G2 通过**（CS-216）；① 在线会话技术选型确认（自研轮询 vs 第三方 SDK）；② 机器人方案确认（关键词/向量检索/第三方 LLM 接口）；③ 客服规模与 SLA 指标确认。
**阶段出口**：CS-310 压测与模块级回归通过（Gate G3）

> 证据统一归档到 `docs/testing/evidence/cs/CS-XXX/`；回归范围固定为 README §8.2 的 R1~R7 + 一二期客服模块全量用例。

## 批次 A：在线即时会话（CS-301 ~ CS-304）

### CS-301 [DBA] 在线会话表与客服负载 / 技能组表
| 项 | 内容 |
|----|------|
| 阶段/主线 | 三期 / 数据扩展 |
| 对应功能 | §2.1 在线客服入口、§11 后续扩展 |
| 依赖 | 二期 CS-216（Gate G2） |
| 关联 | CS-302、CS-304、CS-307 |
| 预估 | 1.5 人天 |

**目标**：为在线会话、客服在线状态、会话分配与技能组建立数据模型。

**实现的功能**
- 会话与消息表（`cs_chat_session`、`cs_chat_message`）
- 客服在线状态与并发承载数（`cs_agent_status`）
- 技能组与客服技能（`cs_skill_group`、`cs_agent_skill`）

**实现步骤**
1. `cs_chat_session`：`id`、`session_no`(varchar 32, unique)、`user_id`(bigint)、`agent_id`(bigint nullable)、`ticket_id`(bigint nullable，会话转工单时回填)、`type_id`(bigint nullable)、`status`(varchar 16：`waiting`/`serving`/`closed`)、`last_message_at`(timestamp nullable)、`closed_at`(timestamp nullable)、`timestamps`；索引 `[status, last_message_at]`、`[agent_id, status]`、`[user_id, created_at]`。
2. `cs_chat_message`：`id`、`session_id`(bigint)、`sender_type`(varchar 16：`user`/`agent`/`system`/`bot`)、`sender_id`(bigint nullable)、`content`(text)、`images`(json nullable)、`read_at`(timestamp nullable)、`created_at`；索引 `[session_id, created_at]`、`[session_id, read_at]`。
3. `cs_agent_status`：`id`、`agent_id`(bigint unique)、`online`(boolean default false)、`max_concurrent`(smallint default 5)、`current_count`(smallint default 0)、`last_seen_at`(timestamp nullable)、`timestamps`。
4. `cs_skill_group`：`id`、`name`(varchar 64)、`type_ids`(json nullable，可服务工单类型)、`timestamps`；`cs_agent_skill`：`id`、`agent_id`、`group_id`、`level`(smallint default 1)、`timestamps`、唯一索引 `[agent_id, group_id]`。
5. 双库迁移 + 回滚验证（同 CS-101 规范：JSON 用 `json()`，不用 PG 专有类型）。
6. 与 `cs_ticket` 的关系：会话可转工单（回填 `ticket_id`），会话消息**不并入** `cs_ticket_message`（避免两套消息语义混淆），转工单时把会话记录摘要作为工单首条消息。

**测试要求**
- 单元测试：四表字段与唯一约束；会话状态常量；技能组与类型的映射判定。
- 集成测试：双库迁移/回滚；会话 + 消息写入与读取；会话转工单回填 `ticket_id`；客服状态并发计数更新（`current_count` 不越界）。
- 回归测试：**R1 订单**、**R2 退款**（新增表不影响既有）；一二期客服模块用例无回退。

**验收标准（Acceptance Criteria）**
- AC-301.1 四张表在双库下创建成功，字段与索引符合设计。
- AC-301.2 会话与工单消息严格分离，转工单只回填关联不复制消息流。
- AC-301.3 `cs_agent_status.current_count` 有并发保护（不出现负数或超过 `max_concurrent`）。
- AC-301.4 迁移可回滚、可重复执行。
- AC-301.5 既有客服模块用例全绿。

**验收证据**：`sql-CS-301.md`、`migrate-status-CS-301.txt`、`pest-CS-301.txt`、`commit-CS-301.txt`

### CS-302 [BE] 在线会话接口与 ChatProvider 适配层
| 项 | 内容 |
|----|------|
| 阶段/主线 | 三期 / 实时通信（关键技术风险） |
| 对应功能 | §2.1 在线客服入口、§11 对接第三方在线客服 |
| 依赖 | CS-301 |
| 关联 | CS-303（用户端）、CS-304（客服端）、CS-305（机器人接入同一消息通道） |
| 预估 | 3.0 人天 |

**目标**：建立会话通道抽象（`CsChatProvider`），先以自研轮询实现，保留切换到第三方（美洽/环信等）或 WebSocket 的能力，避免前端被具体通道绑死。

**实现的功能**
- 会话创建/接入/关闭接口（用户端 + 客服端）
- 消息发送与拉取（游标式增量拉取）
- `CsChatProvider` 抽象层 + 自研轮询实现（`PollingChatProvider`）
- 会话转工单
- 未读计数与已读回执

**实现步骤**
1. 抽象接口 `App\Services\Cs\Contract\CsChatProvider`：`createSession()`、`send()`、`fetch($sessionId, $afterId)`、`close()`、`unreadCount()`。
2. 自研实现 `PollingChatProvider`（基于 CS-301 的表）：
   - 消息增量拉取：`GET /api/cs/chat/{session}/messages?after_id=`，返回新消息；前端 3~5 秒轮询（无新消息时返回空数组，响应体尽量小）
   - 已读：客服/用户拉取即更新 `read_at`（批量更新）
3. 路由（用户端 `auth:sanctum`）：
   - `POST /api/cs/chat/sessions`（创建/复用进行中会话）
   - `GET /api/cs/chat/sessions/{id}`、`POST /api/cs/chat/sessions/{id}/messages`、`GET .../messages?after_id=`、`POST .../close`
4. 路由（后台 `permission:cs.ticket.handle`）：
   - `GET /api/admin/cs/chat/sessions?status=waiting`（待接入会话池）
   - `POST /api/admin/cs/chat/sessions/{id}/accept`（接入，写 `agent_id` + `serving`，`current_count+1`）
   - `POST /api/admin/cs/chat/sessions/{id}/messages`、`POST .../close`
   - `POST /api/admin/cs/chat/sessions/{id}/to-ticket`（会话转工单，复用 CS-105 建单）
5. 并发与一致性：
   - 接入会话用条件更新（`WHERE status='waiting'`），命中 0 行 = 已被他人接入 → 40009
   - `current_count` 用原子增减，关闭会话时 −1 且 `WHERE current_count>0`
6. 降级开关：配置 `cs.chat_enabled`（默认 false），关闭时用户端入口隐藏并回落「提交工单」。
7. 消息长度与图片限制沿用 CS-105 规则（图片 ≤ 9 张），防止两套口径。

**测试要求**
- 单元测试（≥6 条）：Provider 接口契约（mock 实现可替换）；游标增量拉取只返回新消息；已读批量更新；接入会话条件更新冲突；`current_count` 原子增减边界（0 不减、上限不增）；转工单参数映射。
- 集成测试（≥10 条）：
  1. 创建会话返回 session_no；
  2. 用户发消息 → 客服拉取可见；
  3. 客服接入后状态变 `serving`；
  4. 两个客服同时接入只有一个成功（40009）；
  5. 游标拉取不重复不遗漏（构造 20 条消息分 3 次拉取）；
  6. 已读后 `unreadCount` 归零；
  7. 关闭会话释放 `current_count`；
  8. 会话转工单生成工单且消息摘要正确；
  9. 未登录/无权限分别 401/403；
  10. `chat_enabled=false` 时接口拒绝且前端入口隐藏。
- 回归测试：**R3 通知**（会话消息是否走站内信需明确，默认不重复通知）、**R4 权限**。

**验收标准（Acceptance Criteria）**
- AC-302.1 `CsChatProvider` 抽象成立：替换实现（mock）不影响上层调用。
- AC-302.2 消息增量拉取不重不漏（20 条分 3 次拉取结果完整且有序）。
- AC-302.3 并发接入只有一个成功，冲突返回 40009。
- AC-302.4 `current_count` 在接入/关闭后准确，不越界（0 ≤ count ≤ max）。
- AC-302.5 会话转工单数据完整（类型、订单、描述摘要）。
- AC-302.6 降级开关生效：关闭后无会话入口且不报错。
- AC-302.7 消息规则与工单一致（长度、图片数量）。

**验收证据**：`pest-CS-302.txt`、`pest-pgsql-CS-302.txt`、`curl-CS-302.md`（含并发接入冲突演示）、`loadtest-CS-302.md`（并发拉取一致性）、`commit-CS-302.txt`

### CS-303 [WEB] 在线客服聊天界面
| 项 | 内容 |
|----|------|
| 阶段/主线 | 三期 / 前端 |
| 对应功能 | §2.1 在线客服入口 |
| 依赖 | CS-302 |
| 关联 | 一期 CS-111（首页入口改为在线客服）、CS-305（机器人消息在同一会话流展示） |
| 预估 | 2.5 人天 |

**目标**：用户在服务中心可与客服实时对话（含机器人消息），支持图片、未读提示、会话结束评价入口。

**实现的功能**
- 聊天窗口（消息流 + 输入框 + 图片）
- 轮询拉取与自动滚动
- 排队提示（等待接入）
- 会话结束（转工单 / 关闭）
- 机器人消息样式区分

**实现步骤**
1. 页面 `web/src/views/ChatView.vue`（路由 `/service-center/chat`），首页「联系客服」根据 `chat_enabled` 决定跳聊天还是提单。
2. 消息流：区分我方/客服/系统/机器人四种气泡；图片可预览；新消息自动滚动到底部（用户上滑查看历史时暂停自动滚动）。
3. 轮询：进入页面拉取全量 → 定时 3 秒拉取增量（`after_id`）→ 页面隐藏时暂停轮询（`visibilitychange`）；失败指数退避 + 提示。
4. 排队态：未接入时展示「正在为您接入客服…」+ 等待时长；超过配置时长（如 60 秒）提示「可先提交工单」并提供入口。
5. 输入：文本 + 图片（复用 `POST /api/cs/upload-image`）；发送中态、失败重发（保留内容）。
6. 结束会话：用户主动结束 → 提示是否转工单（保留会话记录摘要）。
7. H5 适配：输入框固定底部，键盘弹起时消息流滚动到底；消息气泡最大宽度 75%。

**测试要求**
- 前端单元测试（`web/tests/cs-chat.test.ts`，≥6 条）：
  1. 四种消息类型渲染样式区分；
  2. 轮询收到新消息后追加到列表；
  3. 上滑查看历史时不自动滚动；
  4. 页面隐藏暂停轮询、恢复后继续；
  5. 发送失败保留内容且可重发；
  6. `chat_enabled=false` 时不展示聊天入口；
  7. 排队态展示等待提示与超时引导。
- 集成测试：mock 轮询接口，模拟 3 轮增量消息，验证消息完整且顺序正确。
- 回归测试：一期 `web/tests/service-center.test.ts`、`cs-ticket.test.ts` 全绿（入口变更不得破坏既有流程）。

**验收标准（Acceptance Criteria）**
- AC-303.1 聊天窗口可发送文本与图片，消息实时展示（轮询延迟 ≤ 5 秒）。
- AC-303.2 增量拉取不重不漏，历史查看体验正常（不跳动）。
- AC-303.3 排队与超时引导正确展示。
- AC-303.4 发送失败可重发，内容不丢失。
- AC-303.5 会话结束可转工单，工单内容含会话摘要。
- AC-303.6 H5 视口下输入区可用、消息流不被键盘遮挡。
- AC-303.7 既有服务中心与工单用例全绿。

**验收证据**：`vitest-CS-303.txt`、`ui-CS-303-chat.png`、`ui-CS-303-mobile.png`、`commit-CS-303.txt`

### CS-304 [ADMIN] 客服会话工作台（多会话并发接待）
| 项 | 内容 |
|----|------|
| 阶段/主线 | 三期 / 前端（后台） |
| 对应功能 | §4.1 工单工作台（扩展为会话 + 工单） |
| 依赖 | CS-302 |
| 关联 | CS-114（工单工作台并行）、CS-307（负载均衡分配结果在此体现） |
| 预估 | 2.5 人天 |

**目标**：客服可同时接待多个会话，左右分栏切换，达到承载上限时不再被分配新会话。

**实现的功能**
- 会话列表（待接入池 + 我的进行中 + 已结束）
- 多会话并发接待（左侧会话列表 + 右侧消息区）
- 接入/转交/关闭会话
- 会话转工单
- 在线状态与承载量展示（当前 N / 上限 M）

**实现步骤**
1. 页面 `admin/src/views/cs/CsChatView.vue`，路由 `/cs/chat`（权限 `cs.ticket.handle`）。
2. 三栏布局：左（会话列表：待接入 / 我的 / 已结束 三个 Tab，含未读角标）、中（消息流）、右（用户信息 + 关联订单 + 操作）。
3. 待接入池：轮询刷新（3 秒），「接入」按钮用条件更新（被抢先接入时提示「已被其他客服接入」）。
4. 我的会话：多路并发，未读角标按会话聚合；切换会话时更新已读。
5. 操作：转交其他客服（在线且未达上限的客服列表）、关闭会话、转工单（弹窗选类型 + 关联订单）。
6. 顶部状态条：在线/离线切换 + `current_count / max_concurrent`；离線后不再被自动分配（与 CS-307 联动）。
7. 与工单工作台的关系：两个页面并存（菜单并列），不强行合并，避免 MVP 已验证的工单交互被破坏。

**测试要求**

  3. 接入失败（已被接入）提示正确；
  4. 切换会话触发已读；
  5. 达到承载上限时「接入」按钮禁用；
  6. 在线/离线切换触发正确接口。
- 集成测试：mock 待接入池轮询 → 接入 → 收发消息 → 转工单 全流程。
- 回归测试：**R7 菜单**（新菜单 icon 双注册）；一期 `admin/tests/cs-ticket.test.ts` 全绿。

**验收标准（Acceptance Criteria）**
- AC-304.1 会话三态列表正确，未读角标准确。
- AC-304.2 并发接待多个会话互不干扰，切换即已读。
- AC-304.3 接入冲突提示友好（被抢先接入时明确提示）。
- AC-304.4 达承载上限时禁止接入并提示。
- AC-304.5 转工单数据完整，工单工作台可见。
- AC-304.6 在线状态与承载量实时展示。
- AC-304.7 既有工单工作台与侧栏用例全绿。

## 批次 B：智能化与 SLA（CS-305 ~ CS-307）

### CS-305 [BE] 智能客服机器人（FAQ 匹配 + 转人工）
| 项 | 内容 |
|----|------|
| 阶段/主线 | 三期 / 智能化 |
| 对应功能 | §11 智能客服机器人（基于 FAQ 的自动回复） |
| 依赖 | 一期 CS-104（FAQ 搜索）、二期 CS-210（看板数据） |
| 关联 | CS-303（会话中的机器人消息）、CS-308（无结果词反哺） |
| 预估 | 3.0 人天 |

**目标**：用 FAQ 内容自动回答高频问题，未命中或用户要求人工时无缝转人工，降低人工会话量。

**实现的功能**
- 问题匹配（关键词 + 分词打分，命中返回 Top-N 文章）
- 会话/工单前置自动回复（置信度高时直接回答，低时给候选 + 转人工）
- 未命中记录（沉淀到搜索无结果词，供 CS-308 分析）
- 机器人回复标记（`sender_type=bot`）与「是否有帮助」反馈
- 转人工入口（会话接入客服 / 引导提工单）

**实现步骤**
1. 服务 `App\Services\Cs\CsBotService`：
   - `answer(string $question, ?int $typeId = null): BotAnswer`（返回 `matched` 布尔、`articles` Top3、`confidence` 0~1、`reply` 文案）
   - 匹配算法（MVP 不引入外部依赖）：标题/同义词/关键词加权打分 → 归一化置信度；`confidence ≥ 0.7` 直接回答，`0.4~0.7` 给候选列表 + 「以上没解决？转人工」，`< 0.4` 直接引导转人工
   - 只匹配 `status=published` 的文章
2. 接入点：
   - 会话：用户首条消息触发自动回复（配置 `cs.bot_enabled`，默认 false，灰度开启）
   - 工单：提交工单时若命中高置信度文章，在自动回复欢迎语后追加「您可能想问」候选（不阻断人工流程）
3. 反馈闭环：机器人回复支持「有帮助/没帮助」（复用 CS-104 反馈接口，增加来源标记 `source=bot`），无帮助则引导转人工。
4. 未命中记录：写入 `cs_faq_search_log`（`keyword`、`hit_count`、`created_at`）—— 本任务补该表（字段：`id`、`keyword`(varchar 100)、`source`(varchar 16：`user`/`chat`/`ticket`)、`hit_count`(integer)、`created_at`，索引 `[keyword]`、`[created_at]`）。
5. 安全与兜底：机器人不得回答订单金额/退款结论类问题（涉及资金与承诺的一律转人工）；敏感词命中直接转人工。
6. 可观测：记录命中率（命中会话数 / 总会话数），供 CS-309 报表。

**测试要求**
- 单元测试（≥8 条）：打分与置信度阈值行为（高/中/低三档）；只匹配已发布文章；同义词命中；类型过滤；Top-N 排序稳定；未命中返回转人工引导；`hit_count=0` 时记录；敏感词/资金类问题强制转人工。
- 集成测试（≥7 条）：
  1. 会话首条消息触发机器人回复；
  2. 高置信度直接给出答案；
  3. 低置信度给候选 + 转人工；
  4. 未命中写入 `cs_faq_search_log`；
  5. 机器人回复标记 `sender_type=bot` 且用户端样式区分；

### CS-306 [BE] SLA 超时预警与工单升级
| 项 | 内容 |

**目标**：对超过承诺时效未首次回复 / 未解决的工单自动预警与升级（标记紧急 + 通知主管），把「事后统计」变成「事中干预」。

**实现的功能**

### CS-307 [BE] 多客服负载均衡分配 + 技能组
| 项 | 内容 |
|----|------|
| 阶段/主线 | 三期 / 规模化 |
| 对应功能 | §11 多客服负载均衡分配 |
| 依赖 | CS-301、二期 CS-212（已有数据权限与分配基础） |
| 关联 | CS-304（会话工作台体现分配结果）、CS-309（绩效报表） |
| 预估 | 2.0 人天 |

**目标**：新工单/新会话按「在线 + 技能匹配 + 负载最低」自动分配，避免抢单混乱与忙闲不均。

**实现的功能**
- 分配策略（在线优先 → 技能匹配 → 负载最低 → 轮询兜底）
- 自动分配（工单创建时、会话接入前）
- 手动分配仍可覆盖（人工优先）
- 分配日志（谁在什么时候被分配到什么，供绩效与复盘）

**实现步骤**
1. 策略服务 `CsAssignmentService::assign(CsTicket|CsChatSession $target, ?int $typeId = null): ?int`（返回 `agent_id`，无可用客服返回 null 并留未分配）：
   - 候选集：`cs_agent_status.online = true` 且 `current_count < max_concurrent`
   - 技能过滤：`cs_agent_skill.group_id` 对应技能组的 `type_ids` 命中工单类型（无技能组限制时不过滤）
   - 排序：`current_count` 升序 → 同负载按 `last_assigned_at` 升序（轮询）→ `id` 升序（稳定）
   - 无在线客服 → 留未分配，返回 null（不抛错），状态保持 `pending`
2. 触发点：
   - 工单创建（CS-105 钩子，配置 `cs.auto_assign_enabled`，默认 true）
   - 会话接入前预分配（会话保持 `waiting`，由 CS-302 的 accept 确认）
3. 并发安全：`current_count` 用原子条件更新 `WHERE current_count < max_concurrent`，命中 0 行则换下一个候选（避免超分配）。
4. 分配记录：写 `cs_ticket.assignee_id` + 系统消息「已分配给 X」；会话同理。
5. 手动覆盖：后台分配接口（二期 CS-212）优先于自动分配，手动分配后不再自动改派。
6. 重新分配（SLA 升级场景）：`reassign()` 排除原处理人后按同一策略选取。

**测试要求**
- 单元测试（≥6 条）：候选过滤（离线/满载被排除）；技能匹配；负载排序与同载轮询；无可用客服返回 null；并发分配不超 `max_concurrent`；重新分配排除原处理人。
- 集成测试（≥7 条）：
  1. 建单自动分配给在线且负载最低的客服；
  2. 全部离线时保持未分配且不报错；
  3. 全部满载时保持未分配；
  4. 技能不匹配时不分配；
  5. 20 个工单并发分配给 3 个在线客服，无人超过 `max_concurrent`（**并发硬指标**）；
  6. 手动分配覆盖自动分配后不再改派；
  7. 分配产生系统消息与日志。
- 回归测试：**R4 权限**（分配不改变权限模型）、一二期工单分配用例全绿。

**验收标准（Acceptance Criteria）**
- AC-307.1 分配策略按「在线 → 技能 → 负载 → 轮询」执行，结果可解释（记录决策日志）。
- AC-307.2 无可用客服时保持未分配，不抛错、不阻塞建单。
- AC-307.3 **并发 20 单分给 3 客服，无人超过 `max_concurrent`**（硬指标）。
- AC-307.4 手动分配优先且不被自动改派。
- AC-307.5 分配产生系统消息，处理人可追溯。
- AC-307.6 既有权限与分配用例全绿。

**验收证据**：`pest-CS-307.txt`、`loadtest-CS-307.md`（20 并发分配结论）、`sql-CS-307.md`（分配结果核对）、`commit-CS-307.txt`
