### T-055 [DBA/BE] 积分三表与 PointService
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P3 / 留存线 |
| 对应功能 | F09 |
| 依赖 | T-002（确认收货作为入账时点） |
| 关联 | T-056、T-057 依赖本任务；T-058 前端展示 |
| 预估 | 1.5 人天 |

**目标**：建立积分账户与流水模型，**余额由流水驱动**（可对账，不做无来源的余额修改）。

**实现步骤**
1. 迁移三表：`points`（`user_id` 主键、`balance`）、`point_logs`（`user_id`、`type`、`change`（正负）、`balance_after`、`ref_type`、`ref_id`、时间戳）、`sign_ins`（`user_id`、`sign_date`、`streak`，唯一 `(user_id, sign_date)`）。
2. 索引：`point_logs(user_id, id)`、`sign_ins(user_id, sign_date)`。
3. `PointService`：
   - `earn($userId, $change, $type, $refType, $refId, $remark)`：事务内更新 `points.balance` 并写 `point_logs`（`balance_after` 必须等于更新后余额）；
   - `deduct(...)`：余额不足则拒绝（业务码），不使用「先扣后校验」；
   - `balanceOf($userId)`：查 `points`，无记录时按 0 返回并惰性建行；
   - **一致性约束**：任何积分变动必须经 Service，`balance_after` 与 `balance` 强一致；提供 `points:audit` Command 校验「余额 = Σ 流水」并在不一致时告警。
4. 配置项（`system_configs`）：`point.earn_ratio`（实付 1 元 = N 分，默认 1）、`point.deduct_ratio`（100 分 = 1 元）、`point.deduct_min`（抵扣使用门槛，如订单满 20 元可用）、`point.expire_days`（有效期，0 = 永久）。
5. 双库迁移验证。

**测试要求**
- 单元：`earn`/`deduct` 正常与余额不足；`balance_after` 正确性；并发扣减不出现负余额（条件更新）；`points:audit` 检出人为制造的不一致。
- 接口/集成（Pest）：初始化余额、连续变动后余额与流水一致；扣减超余额被拒；未登录 401。
- 回归：既有用户与订单用例全绿（新增表不影响）。

**验收标准**：余额与流水恒等（`points:audit` 通过）；扣减不会出现负余额；配置项可调且生效。

**证据**：`pest-T-055.txt`、`pest-pgsql-T-055.txt`、`sql-T-055.md`（流水与余额核对）、`commit-T-055.txt`

### T-056 [BE] 签到、下单得积分与退款回退
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P3 / 留存线 |
| 对应功能 | F09 |
| 依赖 | T-055 |
| 关联 | T-057 抵扣依赖余额；T-058 前端签到 |
| 预估 | 1.5 人天 |

**目标**：用户有稳定的积分获取途径（签到 + 消费），且退款时按规则回退，账面不虚增。

**实现步骤**
1. 签到 `POST /me/sign-in`：同一 `sign_date` 只能签一次（唯一约束 + 业务校验双保险）；连续签到 `streak` 递增（前一日有签到则 +1，否则重置为 1）；奖励按规则（基础分 + 连续天数加成，规则放 `system_configs` 或常量表）；返回本次获得积分与余额。
2. 消费得积分：监听 **确认收货**（`OrderCompleted` 事件，来自 T-002/T-003）与订单完成状态，按 `pay_amount × earn_ratio` 向上取整入账；`ref_type=order`、`ref_id=order_id`，并以幂等键（订单 id + type）防止重复入账。
3. 退款回退：退款成功时按退款行实付占比回退已入账积分（`type=order_refund_rollback`，`change` 为负）；若积分已被消费导致余额不足，允许余额为 0 并把差额记为负向待补（或按评审结论拒绝退款 —— 需在文档明确，**推荐余额不足时置 0 并记录 `shortage` 字段**）。
4. 积分过期（若配置）：`points:expire` Command（每日），按 `expire_days` 对超过期限的获取记录做扣减（按先进先出规则），写流水；不做则不注册该任务。
5. 接口：`GET /me/points`（余额 + 即将过期提示）、`GET /me/point-logs`（分页流水，含类型友好文案）。
6. 事件挂接写入 T-018 通知（如「签到成功 +N 积分」）；签到后返回连续天数供前端展示。

**测试要求**
- 单元：连续签到 streak 计算（连续/断签/同日重复）；消费积分按实付计算与取整；重复入账幂等；退款回退计算（部分退/全额退）；余额不足回退处理。
- 接口/集成（Pest）：① 签到成功与重复签到被拒；② 跨日连续签到 streak 正确（用时间旅行 `travel()`）；③ 确认收货后积分入账一次且幂等（重复触发不重复入账）；④ 退款后积分回退正确；⑤ 流水分页与筛选；⑥ 未登录 401。
- 回归：订单确认收货、退款用例全绿（积分挂接不改变主流程结果）。

**验收标准**：签到与消费入账准确且幂等；退款回退金额与规则一致；`points:audit` 通过；主流程不受积分异常影响（异常在监听器内捕获记录，不阻断订单）。

**证据**：`pest-T-056.txt`、`sql-T-056.md`（入账与回退流水核对）、`commit-T-056.txt`

### T-057 [BE] 积分抵扣与结算金额明细扩展
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P3 / 留存线 |
| 对应功能 | F09 |
| 依赖 | T-056（T-035 金额链路） |
| 关联 | T-058 前端选择抵扣；T-035 的 `amount_details` 结构扩展 |
| 预估 | 1.5 人天 |

**目标**：积分可当钱花（抵现），且与券/满减共存时金额计算仍然正确。

**实现步骤**
1. `amount_details` 结构扩展（版本号升级为 `v: 2`，向后兼容 v1 的历史订单展示）：新增 `point_used`、`point_deduct_amount`。
2. 下单参数增加 `use_points`（数量或布尔，按评审结论；推荐传数量便于前端控制）。
3. 计算顺序（**评审确认并写入文档**）：商品总额 → 满减 → 券 → **积分抵扣** → 运费 → 应付；约束：抵扣后应付 ≥ 0.01 元（不允许 0 元单，防止支付通道与回调校验异常）；抵扣需满足 `deduct_min`（订单金额门槛）。
4. 抵扣时**先校验余额、事务内扣减**（条件更新：`UPDATE points SET balance = balance - ? WHERE user_id = ? AND balance >= ?`），失败即回滚整单（不允许「订单已建但积分没扣」）。
5. 订单取消/退款时的积分返还：整单取消 → 返还原积分；退款 → 按退款比例返还积分（`type=deduct_revert`），规则与 T-056 的消费回退区分清楚（一个是「退还花的积分」，一个是「扣回赚的积分」），两类流水分别在文档说明。
6. 老订单（无积分）的金额明细展示兼容（缺失字段按 0 处理）。

**测试要求**
- 单元：抵扣计算与取整；「应付 ≥ 0.01」约束；`deduct_min` 门槛；余额不足拒绝；与券叠加的组合计算；返还计算。
- 接口/集成（Pest）：① 用积分下单金额正确并扣减余额；② 余额不足被拒且订单未创建；③ 积分 + 券 + 满减组合金额正确（分摊不变量仍成立）；④ 未达门槛被拒；⑤ 取消后积分返还；⑥ 退款后按比例返还；⑦ 并发下单不出现负余额或超扣。
- 回归：券相关（T-041 矩阵）复跑通过；V1.0 无积分路径金额不变。

**验收标准**：积分抵扣金额与明细正确；任何组合下应付金额校验通过；取消/退款返还金额正确；无负余额（并发验证）。

**证据**：`pest-T-057.txt`、`pest-pgsql-T-057.txt`、`sql-T-057.md`（金额与积分流水核对）、`commit-T-057.txt`

### T-059 [OPS/BE] Meilisearch 部署与商品索引同步
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P3 / 体验与性能 |
| 对应功能 | F10 |
| 依赖 | T-007（属性字段作为索引内容） |
| 关联 | T-060 搜索接口切换；T-062 导入商品后需触发索引 |
| 预估 | 2.0 人天 |

**目标**：商品搜索从数据库 LIKE 迁移到搜索引擎，支持相关性排序与属性筛选。

**实现步骤**
1. 部署：`docker-compose.yml` 增加 `meilisearch` 服务（固定版本、数据卷、`MEILI_MASTER_KEY` 环境变量、仅内网端口）；开发/测试环境的启动说明更新到 DEPLOY 文档。
2. 客户端封装 `MeilisearchClient`（使用官方 PHP SDK 或轻量 HTTP 封装）；`config/search.php` 增加开关 `enabled`（未启用时搜索接口回退数据库查询，保证本地无 Meilisearch 也能跑）。
3. 索引结构 `products`：`id`、`title`、`subtitle`、`keywords`、`category_id`、`category_name`、`brand_id`、`brand_name`、`price`、`sales_count`、`status`、`created_at`、`attributes`（键值对，供筛选）、`spec_values`（规格值文本，供规格关键词匹配）；设置 `searchableAttributes`（title 权重最高）、`filterableAttributes`（category_id/brand_id/status/price/attributes 相关）、`sortableAttributes`（price/sales_count/created_at）。
4. 同步机制：监听商品保存/上下架/删除事件（`ProductSaved`、`ProductStatusChanged`、`ProductDeleted`）→ 入队 `SyncProductToSearch` Job（批量合并、失败重试 3 次）；导入（T-062）完成后批量同步。
5. 全量校准：Command `search:sync`（默认全量重建索引，支持 `--chunk=`），每日 03:00 调度，处理「索引与库不一致」的兜底。
6. 索引安全：只索引 `status=上架` 商品（下架即移除），避免下架商品出现在搜索与联想结果。
7. 文档：索引字段与筛选维度的对应关系写入文档，便于后续加字段。

**测试要求**
- 单元：索引文档组装（含属性扁平化、规格值拼接）；启用/禁用开关分支。
- 接口/集成：商品上架/改价/下架/删除后索引变更（用测试索引断言，或用 mock 客户端断言调用参数）；全量同步后数量与库内上架商品数一致。
- 回归：既有商品列表/搜索接口在 `search.enabled=false` 时行为不变（回退路径必须可靠）。

**验收标准**：索引内容与商品数据一致（数量与抽样字段）；上下架 1 分钟内同步；开关关闭时回退数据库查询且既有用例全绿。

**证据**：`pest-T-059.txt`、`sql-T-059.md`（索引与库内数量对比）、`commit-T-059.txt`

### T-060 [BE] 搜索接口切换、关键词联想与热搜榜
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P3 / 体验与性能 |
| 对应功能 | F10 |
| 依赖 | T-059 |
| 关联 | T-061 前端；T-014 属性筛选语义需一致 |
| 预估 | 1.5 人天 |

**目标**：搜索结果更相关、响应更快，并提供联想与热词。

**实现步骤**
1. `GET /api/storefront/products` 的搜索实现切换：`search.enabled=true` 时走 Meilisearch（关键词、分类、品牌、属性、价格区间、排序全部下推为 filter/sort），返回结构保持与 V1.0 一致（分页字段、商品字段），前端无需改动即可受益。
2. 相关性排序：标题命中权重最高（`searchableAttributes` 顺序控制），其次品牌/分类/描述；无关键词时按 `sort` 参数（销量/价格/时间）。
3. 联想接口 `GET /search/suggest?q=`：返回最多 10 条商品标题 + 命中分类/品牌的联想项；实现方式：Meilisearch 前缀搜索 + 结果标题摘要，加短缓存（如 60s，键含关键词）；**拼音首字母支持**：若引入拼音库成本高则先做「标题子串 + 首字母字段」方案（索引中存 `title_pinyin_initial`，由同步 Job 生成），具体方案在实现时选定并写入文档。
4. 热搜榜 `GET /search/hot`：对搜索关键词计数（Redis 有序集合，无 Redis 时退化为数据库表 `search_keywords` 计数）；每次搜索记录一次（节流、过滤敏感词与超短词）；返回 TOP10，缓存 10 分钟。
5. 无结果推荐：搜索命中 0 条时，返回同分类热销商品（最多 6 个）作为推荐字段，供前端展示。
6. 敏感词与空词处理：空关键词直接返回 422 或空结果（按现有约定）；敏感词返回空结果且不记入热搜。
7. 性能：搜索接口 P95 目标 < 200ms（万级商品），必要时对 Meilisearch 查询加超时控制与降级（超时回退数据库查询）。

**测试要求**
- 单元：过滤条件组装（分类/品牌/属性/价格/排序 → Meilisearch filter）；热词计数节流与敏感词过滤；无结果推荐选择逻辑。
- 接口/集成（Pest）：① 关键词搜索返回结果与 V1.0 结构一致（字段断言）；② 属性筛选与 T-014 语义一致（同属性 OR / 跨属性 AND）；③ 下架商品不出现；④ 联想接口返回结构与缓存；⑤ 热搜前三名计数正确；⑥ 搜索超时降级触发；⑦ 无结果推荐返回内容。
- 回归：V1.0 商品搜索与列表用例在开关关闭时全绿；开启时（CI 可配 Meilisearch 或使用 mock）关键用例通过。

**验收标准**：开关两种模式下接口结构一致；属性筛选行为与一期一致；联想/热搜可用；P95 达标（有压测证据）。

**证据**：`pest-T-060.txt`、`loadtest-T-060.md`（搜索响应时间）、`curl-T-060.md`、`commit-T-060.txt`

3. 冷静期内撤销：用户重新登录 → 提供撤销入口（或首次登录时弹窗询问）→ 清除 `cancel_*` 字段、恢复状态、发通知。
4. 到期执行 Command `accounts:purge-cancelled`（每日）：对 `cancel_effective_at <= now()` 且未撤销的账号做匿名化处理 —— 手机/邮箱/昵称置匿名值、密码置随机、清空头像；**保留订单与其快照数据（法定账务留存）**，用户标识改为匿名实体；清理会话与未使用券/积分（按规则）。
5. 接口：`GET /me/cancel-status`（当前状态与到期时间，供前端展示冷静期）。
6. 日志与合规：申请、撤销、执行都写操作日志（脱敏）；执行结果输出统计。

**测试要求**
- 单元：前置校验（各类未完成单据拒绝）；冷静期到期判定（时间旅行）；匿名化处理不破坏订单外键与快照。
- 接口/集成（Pest）：① 有未完成订单时申请被拒并列出单据；② 无阻碍时申请成功且 Token 全部失效；③ 冷静期内登录撤销成功且状态恢复；④ 到期 Command 执行后用户信息匿名化、订单仍可查（含快照）；⑤ 未登录 401。
- 回归：订单、用户、认证既有用例全绿（匿名化不影响历史订单展示与后台查询）。

**验收标准**：注销全流程与冷静期机制正确；资金与订单安全校验严格；匿名化后历史数据完整可查；执行有据可查。
