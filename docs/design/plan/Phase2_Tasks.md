### T-033 [BE] 领券接口（原子防超发）与我的券接口
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P2 / 留存线 |
| 对应功能 | F06 |
| 依赖 | T-031 |
| 关联 | T-038（前端）、T-034（用券校验读取 user_coupons） |
| 预估 | 1.5 人天 |

**目标**：用户可领券且**并发下不超发**，领到的券可用于下单。

**实现步骤**
1. 领券中心 `GET /coupons`：返回可领券（`status=active`、在有效期内、`issued_count < total_count`），附当前用户已领数量与是否达每人限领。
2. 领取接口 `POST /coupons/{id}/receive`：
   - **原子防超发**：`UPDATE coupons SET issued_count = issued_count + 1 WHERE id = ? AND issued_count < total_count AND status = 'active'`，受影响行数为 0 则返回「已领完」；该方法必须在事务内并配合行级锁语义验证（PG 下条件更新天然原子；SQLite 测试环境注意串行化）。
   - 每人限领校验：`SELECT COUNT(*) FROM user_coupons WHERE user_id=? AND coupon_id=?` < `per_user_limit`（与上述条件更新在同一事务内，防止并发绕过）。
   - `expire_at` 计算并固化：`valid_type=absolute` → `valid_to`；`relative` → `now() + valid_days`。
   - 幂等与重复提交：前端节流 + 后端限领校验双重保护；重复请求返回明确业务码而非 500。
3. 我的券 `GET /me/coupons?status=unused|used|expired|returned`：分页，返回券信息、门槛、适用范围、`expire_at`、临近过期标记（≤3 天）。
4. 结算可用券 `GET /coupons/available?order-context=...`：入参为购物车/结算上下文（商品与金额），返回可用券（满足门槛与适用范围）与不可用原因（门槛不足/范围不符/已过期），供前端展示「为什么不能用」。
5. 定时任务 `coupons:expire`：每小时把 `status=unused` 且 `expire_at < now()` 的置 `expired`（本任务建表后即可接入，逻辑在 T-037 精化）。

**测试要求**
- 单元：`expire_at` 计算（绝对/相对）；可用性判定（门槛、范围、过期）；限领边界。
- 接口/集成（Pest）：① 领取成功并返回券记录；② 达每人限领被拒；③ 领完后被拒；④ 停发的券不可领；⑤ 未登录 401；⑥ 我的券按状态筛选正确；⑦ 可用券接口对门槛不足/范围不符返回不可用原因。
- **并发测试（关键）**：脚本并发（≥50 并发）领取同一张限量 10 的券，断言 `issued_count = 10` 且 `user_coupons` 记录数 = 10（无超发）；写入 `loadtest-T-033.md`。
- 回归：订单与购物车用例全绿。

**验收标准**：并发压测无超发（硬指标）；限领与停发规则准确；可用券接口返回原因正确；测试环境双库通过。

**证据**：`pest-T-033.txt`、`loadtest-T-033.md`（并发结论）、`sql-T-033.md`（`issued_count` 与记录数核对）、`commit-T-033.txt`

### T-034 [BE] 用券校验与金额分摊 Service
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P2 / 留存线（关键路径） |
| 对应功能 | F06 |
| 依赖 | T-033 |
| 关联 | T-035 直接调用；T-036 退款分摊同源；T-041 专项测试对象；三期 T-057 积分抵扣复用同套分摊框架 |
| 预估 | 2.0 人天 |

**目标**：把「券/满减怎么算、怎么摊到行项目、怎么退」这套规则固化成可测试的 Service —— 这是本版本最需要正确性的代码。

**实现步骤**
1. 评审确认规则后实现 `CouponService`：
   - `validateUse(UserCoupon $uc, OrderContext $ctx)`：状态 unused、未过期、门槛满足、适用范围命中（`scope=all/category/product`，多商品时按命中金额计算门槛）。
   - `calculateDiscount()`：券优惠额（fixed 直减；percent 按比例并受 `max_discount` 封顶）、满减优惠额（按订单命中金额取最优梯度）。
   - **分摊算法**：按行项目金额（`price * qty`）占比分摊优惠额，`round(share, 2)`，**尾差记入金额最大的行**；输出 `order_items.coupon_share` / `promotion_share` 与 `orders.amount_details`（含商品总额、券优惠、满减、运费、应付、各行分摊明细）。
   - 叠加规则：券与满减默认可叠加（先满减后券或按评审结论），规则以常量集中定义并注释说明。
2. 分摊不变量（写成断言）：Σ 行分摊 = 总优惠额（误差 0）；任一行实付 ≥ 0；应付 = 商品总额 − 券 − 满减 + 运费 ≥ 0。
3. 边界处理：单商品、多商品不同金额、金额为 0 的赠品行、超过 10 个行项目、行金额极不均衡（1 分与 10000 元并存）。
4. 提供纯函数式接口便于单元测试（不依赖 DB），DB 相关部分抽到 Repository/Service 边界。
5. `amount_details` 结构版本号字段（如 `v: 1`），便于后续口径演进时兼容历史订单展示。

**测试要求**
- 单元（重点，≥12 个用例）：单行/多行分摊；尾差归位；percent 封顶；门槛按命中金额计算；范围筛选（部分商品适用）；Σ 分摊 = 总额不变量；行实付 ≥ 0；极值（0 元行、超大金额）；叠加两种顺序结果一致性与规则断言。
- 接口/集成：通过内部 Service 调用验证（接口层在 T-035 覆盖）。
- 回归：V1.0 不含券的订单金额计算路径不变（`amount_details` 为空时行为与旧版一致）。

**验收标准**：≥12 个单元用例全绿；分摊不变量在任何组合下成立；极端数据无负数与精度错误；规则以文档 + 代码注释双重记录。

**证据**：`pest-T-034.txt`、`sql-T-034.md`（分摊明细核对样例）、`commit-T-034.txt`

### T-035 [BE] 订单金额链路改造与支付回调校验扩展
| 项 | 内容 |

| 阶段/主线 | V1.1-P2 / 留存线（关键路径） |
| 对应功能 | F06 |

**目标**：下单时可用券，订单金额字段与分摊快照完整落库，支付回调金额校验覆盖优惠后金额。

**实现步骤**
1. `POST /orders` 增加可选参数 `user_coupon_id`、`promotion_id`（或不传时自动匹配最优满减，按评审结论），并保留 V1.0 不传券的行为完全不变。
2. 下单事务内：校验券归属与可用性（T-034）→ 计算分摊 → 写 `orders` 金额字段与 `amount_details` → 写各行 `coupon_share`/`promotion_share` → **锁定券**（`user_coupons.status` 保持 unused 但记录占位，或按评审结论直接置 used 并保留取消返还能力，方案需在代码注释与文档明确）。
3. 库存锁定与金额计算顺序：先校验券再锁库存（避免锁了库存因券无效回滚），回滚时券状态一并恢复（事务保证）。
4. 支付回调金额校验扩展：V1.0 的 `bccomp` 校验对象由 `pay_amount` 改为「按 `amount_details` 重算应付」并与回调金额比对（容忍 0.00 差异），不一致则拒绝并告警日志。
5. 订单详情/列表响应补充：`discount_amount`、`promotion_discount`、`amount_details`，前端可展示明细；历史订单（无券）返回 0 与空明细，前端兼容。
6. 订单超时取消（`orders:auto-cancel`）时释放券（与 T-036 一致的返还逻辑，本任务先留挂接点）。

**测试要求**
- 单元：金额校验重算函数；不传券时与 V1.0 结果完全一致（diff 断言）。
- 接口/集成（Pest）：① 不带券下单金额与 V1.0 一致；② 带券下单金额正确且明细完整；③ 券无效（过期/门槛不足/范围不符）下单被拒；④ 他人券 403；⑤ 支付回调金额不匹配被拒（业务码 + 日志）；⑥ 回调成功订单状态与金额正确；⑦ 并发下同一张券不能被两个订单同时使用。

**验收标准**：无券路径与 V1.0 行为完全一致（用例断言证明）；用券订单金额与分摊明细正确；回调校验覆盖优惠后金额；并发用券不重复消费。

### T-036 [BE] 取消/退款与券回退逻辑
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P2 / 留存线（关键路径） |
| 对应功能 | F06 |
| 依赖 | T-035 |
| 关联 | T-041 专项；T-054 二期验收 |
| 预估 | 1.5 人天 |

**目标**：用券订单在取消或退款时，金额与券的状态都正确回退，不产生资损与券泄漏。

**实现步骤**
1. 整单取消（`pending_payment` 取消 / 超时取消）：券返还（`user_coupons.status` 恢复 unused；若期间已过期则不返还或按评审结论置 expired，需在文档明确）；`coupons.used_count` 回退（若在下单时已计）。
2. 退款（用户申请 + 后台审核通过）：
   - **按行项目实付退款**：单行退款金额 = `price*qty − coupon_share − promotion_share`；足额整单退款时校验 Σ 行实付 = 订单实付（含运费处理规则，发货前退运费/发货后退运费需明确）。
   - 部分退款后券是否返还：按评审结论实现（默认不返还已使用券，除非整单退款），规则写入注释与文档。
   - 退款金额校验：后台审核页展示可退上限，超限拒绝。
3. 退款金额落到 `refunds` 表（V1.0 已有表，确认字段够用，不够则加列）。
4. 一致性断言：`Σ 行实付 + 运费处理 = 订单实付`；退款累计不得超过订单实付。
5. 与状态机联动：退款中/已退款状态下券与金额不可再变（防重复退款与重复返券）。
6. 操作日志记录券返还与退款金额变更。

**测试要求**
- 单元：单行/多行部分退款金额计算；整单退款校验不变量；券返还判定（正常/已过期/部分退款）。
- 接口/集成（Pest）：① 未支付取消 → 券返还可用；② 超时取 consuming 券 → 券按规则处理；③ 申请退款 → 后台通过 → 退款金额 = 行实付；④ 部分退款 → 剩余可退金额正确；⑤ 重复退款被拒；⑥ 退款不返还券场景券状态正确。
- 回归：V1.0 无券退款全流程用例全绿（金额不变）。

**验收标准**：券状态与金额回退全部符合规则；不变量成立；重复操作幂等；无券旧流程零回归。

**证据**：`pest-T-036.txt`、`sql-T-036.md`（退款金额与券状态核对）、`curl-T-036.md`、`commit-T-036.txt`

### T-037 [BE] 券过期任务与满减匹配
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P2 / 留存线 |
| 对应功能 | F06 |
| 依赖 | T-034 |
| 关联 | T-033 的 `coupons:expire` 落地；T-039 展示满减标签 |
| 预估 | 1.0 人天 |

**目标**：过期券自动失效（用户端状态准确）；满减活动在结算时正确匹配最优梯度。

**实现步骤**
1. `coupons:expire` 完善：批量（分批 500）把 `unused` 且 `expire_at < now()` 置 `expired`；记录处理数量；每小时调度（`withoutOverlapping`）。
2. 发券时即将过期提示数据：为 T-019 通知预留「券即将过期」事件（可选，二期末尾按需接通，先留挂接点）。
3. 满减匹配：`PromotionService::match(OrderContext)` —— 找出与商品范围命中且活动时间有效的活动，按命中金额取**最优梯度**（同一活动内取最大优惠），多活动并存时按评审结论（默认取最优一个，不叠加）。
4. 满减展示数据接口：供详情页/结算页展示「满 X 减 Y」标签（活动基本信息与命中提示）。

5. 手动重试接口 `POST /admin/shippings/{id}/pull`（后台单条重试）；批量重试按 `failed` 筛选。
6. 原始报文保存到 `shipping_traces.raw`，便于问题排查与渠道切换时的数据回填。
7. 配置：渠道密钥放 `.env`（`SHIPPING_CHANNEL`、`SHIPPING_CHANNEL_KEY` 等），未配置时 Job 直接跳过并输出提示日志（保证本地开发与测试环境可跑）。
