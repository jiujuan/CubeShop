### T-070 [QA] V1.0 + V1.1 全量回归
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P4 / 回归 |
| 依赖 | T-030、T-054、T-069（三个阶段出口通过） |
| 关联 | T-071/T-072/T-073 均基于本任务的环境与数据准备 |
| 预估 | 1.5 人天 |

**目标**：一次性证明「V1.1 的全部改动没有破坏 V1.0 的任何能力」。

**实现步骤**
1. 环境准备：后端跑在 8000（`php D:/codeproject/PHP/CubeShop/backend/artisan serve --host=127.0.0.1 --port=8000`，注意使用绝对路径与 `cd` 到 backend 目录以免工作目录回收导致失败）；前端 web 与 admin 分别起 dev 服务；PG 测试库 `cubeshop_test` 就绪。
2. 后端全量：`composer test`（SQLite 内存库）+ `composer test:pgsql`（PG）；统计用例总数、通过数、耗时。
3. 前端全量：admin 与 web 两个工程分别 `npm run test`、`npm run typecheck`、`npm run build`（构建必须成功，作为发布前置）。
4. 冒烟脚本：扩展后的 `docs/testing/smoke_test.sh` 全量执行（V1.0 十五项 + V1.1 增量项），要求 100% 通过。
5. 端到端手工全链路（对照路线图 §3.4 验收标准）：
   注册 → 领券 → 浏览（属性筛选）→ 加购 → 用券 + 积分下单 → 支付 → 后台发货（录单号）→ 物流轨迹 → 确认收货 → 评价 → 商家回复 → 积分入账 → 退款（含券与积分回退）→ 报表核对。
6. 缺陷收敛：所有发现的问题开单（含复现步骤、环境、日志、截图），按等级分类；P0/P1 必须修复并回归验证。
7. 输出 `full-regression-v1.1.md`：用例统计表、缺陷清单、链路演示记录、结论。

**测试要求**
- 回归：V1.0 全部用例（含 25+ 回归、111+ 单测/特性测试）与 V1.1 新增用例全绿。
- 集成：端到端链路 1 次完整成功演示（含截图与关键 SQL 佐证）。
- 构建：前端两工程 build 与 typecheck 通过。

**验收标准**：无 P0/P1 缺陷；全链路演示成功；双库全绿；构建通过。

**证据**：`full-regression-v1.1.md`、`pest-all.txt`、`pest-pgsql-all.txt`、`vitest-web-all.txt`、`vitest-admin-all.txt`、`build-T-070.txt`、`e2e-screenshots/`

### T-071 [QA] PG 兼容性与双库专项
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P4 / 回归 |
| 依赖 | T-070 |
| 关联 | V1.0 已建每日 09:00 PG 回归自动化，本任务确认其覆盖 V1.1 新用例 |
| 预估 | 1.0 人天 |

**目标**：确保 V1.1 新增的表、字段、SQL 在 PostgreSQL 下与 SQLite 行为一致，避免「测试过了生产炸」。

**实现步骤**
1. 迁移专项：在 PG 上执行 `migrate:fresh` 与 `migrate`（增量），确认 V1.1 新增约 22 张表全部落地、索引与外键正确、回滚（`migrate:rollback`）可用。
2. 类型兼容复查：JSON/JSONB 字段读写、`DECIMAL` 精度（金额分摊）、时间与时区（`TIMESTAMPTZ` vs `TIMESTAMP` 对 `auto_complete` / `expire` 判定的影响）、序列与自增在事务回滚后的行为（V1.0 曾因序列不回滚导致硬编码 id 失败，改用工厂方法 —— 新用例不得再硬编码 id）。
3. 用例全量双库执行并对比：同一批 Feature 用例在 SQLite 与 PG 下的通过情况；不一致项逐一排查（多为 SQL 方言或类型隐式转换）。
4. 并发用例在 PG 上复跑：券领取（T-033）、用券下单（T-035）、确认收货幂等（T-002）、盘点单号唯一（T-064）—— PG 行锁语义与 SQLite 不同，必须实测。
5. 更新每日 09:00 自动化任务的覆盖范围（确保新用例包含在内）。
6. 输出 `pg-compat-v1.1.md`：迁移清单、差异项与结论、并发复跑结果。

**测试要求**
- 回归：双库全量用例通过率 100%。
- 集成：迁移与回滚双向可用；并发用例在 PG 上无超发/超卖/重复写入。

**验收标准**：PG 与 SQLite 结果一致（或差异有明确解释与修复）；迁移回滚可用；并发结论达标；自动化任务覆盖新用例。

**证据**：`pg-compat-v1.1.md`、`pest-pgsql-all.txt`、`migrate-logs-T-071.txt`、`loadtest-pg-T-071.md`

### T-072 [QA] 并发压测（锁库存 / 发券 / 用券）
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P4 / 性能与安全 |
| 依赖 | T-070 |
| 关联 | T-041 专项的规模化复跑（V1.0 P7 压测方案复用） |
| 预估 | 1.0 人天 |

**目标**：用规模化的并发验证「不超卖、不超发、不重复消费券、金额不错乱」这四条底线。

**实现步骤**
1. 场景清单（沿用 V1.0 P7 压测脚本框架，扩展券与积分）：
   - A 下单锁库存：库存 100 的商品，200 并发下单 → 断言成功 100、无超卖、库存不为负；
   - B 领券防超发：限量 50 的券，500 并发领取 → 断言 `issued_count = 50`、记录数 = 50；
   - C 用券唯一性：单张券被 20 个订单并发使用 → 断言仅 1 单成功用券；
   - D 积分扣减：余额 1000 分账号，10 并发各扣 500 → 断言成功 2 次、余额 0、无负值；
   - E 混合场景：下单 + 支付回调 + 发货 + 确认收货 全链路并发（模拟 50 用户）→ 断言订单状态与金额、库存、券、积分四项总账一致。
2. 数据核验脚本：压测前后对 `inventories`、`coupons.issued_count`、`user_coupons`、`points`、`orders` 做总账对比（SQL 输出到证据文件）。
3. 记录关键指标：QPS、P95/P99 响应时间、错误率、数据库连接占用、慢查询。
4. 压测后回归：跑一遍核心用例，确认压测产生的数据未污染（压测在独立库执行）。
5. 输出 `loadtest-v1.1.md`：场景、参数、结果、总账核对、结论（是否达标）。

**测试要求**
- 并发：5 个场景全部满足断言（无超卖、无超发、无重复消费、无负余额）。
- 回归：压测后核心用例全绿。
- 性能：P95 达到预设目标（若未达标记录瓶颈与优化项）。

**验收标准**：四条底线全部验证通过并有 SQL 总账佐证；有明确结论可写入发布说明。

**证据**：`loadtest-v1.1.md`、`sql-audit-T-072.md`、`loadtest-raw-T-072.log`

### T-073 [QA] 性能基线与接口优化
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P4 / 性能 |
| 依赖 | T-070 |
| 关联 | T-060 搜索性能、T-020 报表性能、T-021 图表加载 |
| 预估 | 1.0 人天 |

**目标**：建立并确认 V1.1 的性能基线，消灭明显慢查询与不必要的请求。

**实现步骤**
1. 基线测量（固定数据集：1 万商品 / 1 万订单 / 1 万用户）：
   | 接口 | 目标 P95 |
   |------|----------|
   | 商品列表 / 属性筛选 | < 300ms |
   | 搜索 / 联想 | < 200ms |
   | 商品详情（含评价汇总） | < 300ms |
   | 订单列表（含 tab 与检索） | < 400ms |
   | 报表趋势（30 日） | < 1s |
   | 物流轨迹查询 | < 300ms |
2. 慢查询排查：开启慢查询日志，对订单列表（多条件 + 分页）、报表聚合、评价汇总、Meilisearch 未命中降级路径逐一分析，补必要索引（`orders(status, created_at)`、`orders(user_id, status)`、`order_items(product_id)`、`reviews(product_id, status)`、`shipping_traces(shipping_id, occurred_at)`）。
3. 缓存复核：商品评分汇总、首页布局、热搜、分类树等缓存命中率与失效正确性（避免缓存导致的脏数据）。
4. N+1 排查：订单列表（用户/地址快照/行项目）、评价列表（商品/用户）、收藏列表（商品）使用 `with()` 预加载。
5. 前端性能抽查：首页与列表页首屏渲染（图片懒加载、骨架屏、图表按需加载 ECharts）。
6. 输出 `perf-baseline-v1.1.md`：基线数据表、优化项与前后对比、遗留瓶颈与建议。

**测试要求**
- 性能：上表各接口达标（未达标项需有优化记录或明确标注为已知瓶颈）。
- 回归：优化后全量用例全绿（索引与预加载不得改变业务行为）。

**验收标准**：基线数据成文；不达标项有分析；优化后无明显 N+1 与慢查询。

**证据**：`perf-baseline-v1.1.md`、`slow-query-T-073.log`、`explain-T-073.md`（关键 SQL 执行计划）

### T-075 [OPS] 部署、迁移脚本与回滚方案
| 项 | 内容 |
|----|------|
| 阶段/主线 | V1.1-P4 / 运维 |
| 依赖 | T-073、T-074 |
| 关联 | T-076 文档同步、T-077 发布 |
| 预估 | 1.0 人天 |

**目标**：V1.1 能在目标环境一次部署成功，出问题能快速回滚。

**实现步骤**
1. 部署清单更新（`docs/DEPLOY.md`）：
   - 新增环境变量（Meilisearch 地址与 key、快递渠道 key、SMTP、队列驱动、缓存驱动、`search.enabled` 开关）；
   - 新增服务（Meilisearch 容器、队列 worker 常驻进程 — 邮件/导出/索引/导入均依赖队列）；
   - 新增定时任务（`orders:auto-complete` 每小时、`shipping:pull-traces` 30 分钟、`coupons:expire` 每小时、`points:expire` 每日、`search:sync` 每日 03:00、`exports:clean` 每日 04:00、库存预警每日 08:00）；
   - 存储目录权限（导出文件、上传图片）、队列失败表 `failed_jobs` 监控。
2. 迁移脚本与顺序：结构迁移 → 数据迁移（属性）→ 索引初始化（`search:sync`）→ 缓存预热；每步附校验 SQL。
3. 回滚方案：
   - 代码回滚（保留上一版本镜像/包）；
   - 数据库回滚边界（新增列可保留不用，**新增表的数据迁移不回滚**，明确回滚后新功能停用而旧功能可用）；
   - 开关回滚（`search.enabled=false`、不配置快递渠道即走降级、`notify` 邮件关闭）；
   - 触发条件（错误率、核心接口失败、金额/库存异常）。
4. 灰度与开关清单：功能开关列表与默认值（新功能默认开启/关闭的策略），确保任一功能可独立关闭。
5. 演练一次完整部署流程（预发/测试环境），记录耗时与卡点。
6. 输出部署 Runbook（照抄即用的步骤清单）。

**测试要求**
- 集成：在测试环境完整执行一次部署（含 Meilisearch 与队列 worker），功能可用。
- 回归：部署后冒烟脚本通过。
- 回滚：执行一次开关回滚与代码回滚验证。

**验收标准**：Runbook 可直接执行；回滚路径验证通过；开关能独立关闭新功能而不影响旧功能。

**证据**：`deploy-runbook-v1.1.md`、`deploy-dryrun-T-075.md`、`rollback-test-T-075.md`、`env-vars-T-075.md`
