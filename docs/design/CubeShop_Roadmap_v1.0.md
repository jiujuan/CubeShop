# CubeShop 电商系统
## 开发路线图（Roadmap）
**版本**：v1.0（MVP）  
**日期**：2026-09-15  
**关联文档**：CubeShop_PRD_v1.0、CubeShop_Architecture_v1.0、CubeShop_Database_Design_v1.0、CubeShop_API_v1.0

---

## 1. 路线图说明

### 1.1 目标
按阶段交付可运行、可验证的增量成果，优先打通「浏览 → 加购 → 下单 → 支付 → 后台发货」核心交易闭环，再完善运营与体验细节。

### 1.2 原则
| 原则 | 说明 |
|------|------|
| 先闭环后增强 | 先做出能真实下单支付的最小闭环，再补后台与体验 |
| 依赖优先 | 基础设施、认证、公共服务先行 |
| 可演示 | 每个阶段结束都有可演示的功能点 |
| 风险前置 | 支付对接、库存并发等难点尽早验证 |
| 文档同步 | 每阶段结束同步更新接口/表结构变更（如有） |

### 1.3 技术基线（回顾）
- 后端：Laravel 13 + PostgreSQL + Redis（可选）+ Sanctum + spatie/permission
- 前端管理端：Vue 3 + TypeScript + Vite + Tailwind + shadcn-vue
- 用户端：响应式 H5 / 轻量前端（可与管理端共享 API）
- 部署：Docker Compose（Nginx + PHP-FPM + Postgres + Redis）

### 1.4 阶段总览

| 阶段 | 名称 | 目标 | 建议周期 |
|------|------|------|----------|
| P0 | 项目脚手架与基础设施 | 可运行的空框架 + 数据库 + 部署骨架 | 3～5 天 |
| P1 | 认证、权限与公共服务 | 登录注册、权限体系、公共基础能力 | 4～6 天 |
| P2 | 商品与分类 | 后台商品管理 + 前台浏览/搜索 | 5～7 天 |
| P3 | 库存、购物车与地址 | 库存锁定、购物车、收货地址 | 4～6 天 |
| P4 | 订单与结算闭环 | 下单、取消、超时、订单查询 | 5～7 天 |
| P5 | 支付与退款 | 支付对接、回调、简单退款 | 5～8 天 |
| P6 | 后台运营完善 | 发货、数据概览、配置、日志、导出 | 4～6 天 |
| P7 | 联调、测试与上线准备 | 全流程测试、修复、部署上线 | 5～7 天 |

> 周期为参考人天（1 名全栈或 1 后端 + 1 前端协作），实际可按团队规模调整。

- [x] 接入 spatie/laravel-permission，初始化角色与权限码
- [x] 权限中间件 / 策略（`can:product.create` 等）
- [x] 公共服务层实现：

  - 配置读取服务

  - 缓存封装、简单限流
- [x] 操作日志写入 `sys_operation_log`

#### 前端任务
- [x] 登录 / 注册页
- [x] Token 持久化与路由守卫
- [x] 动态菜单（根据权限过滤）
- [x] 按钮级权限指令 `v-permission`
- [x] 个人中心基础信息展示与修改

#### 交付物
- 完整认证流程
- 角色权限可配置（至少超管 / 运营）
- 公共 Service 可被后续业务调用

## 3. 阶段依赖关系

```
P0 脚手架
 └─► P1 认证 + 公共服务
      ├─► P2 商品分类
      │    └─► P3 库存 + 购物车 + 地址
      │         └─► P4 订单结算
      │              └─► P5 支付退款
      │                   └─► P6 后台运营
      └──────────────────────────────► P7 测试上线
```

- P2 与 P3 在 P1 完成后可部分并行（前端页面与后端接口）
- P5 依赖 P4 的订单状态机与库存锁定逻辑
- P6 可与 P5 后半段部分并行
- P7 贯穿后期，建议从 P4 起即开始写自动化/手工用例

## 5. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 支付渠道对接慢 / 资质问题 | P5 延期 | 先用沙箱打通回调与状态机；正式商户号并行申请 |
| 库存并发超卖 | 资损 | P3 即实现事务 + 条件更新；P7 做并发压测 |
| 前后端字段不一致 | 联调返工 | 以 API 文档为准，变更及时同步 |
| 需求蔓延 | 整体延期 | 严格按 PRD V1.0 范围，新增需求进 V1.1 |
| 无 Redis 环境 | 缓存/队列能力弱 | 架构已支持 PostgreSQL 降级，P0 验证降级方案 |
