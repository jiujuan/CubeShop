## 1. 路线图说明

### 1.1 规划出发点
V1.0 解决的是「**能不能买**」。V1.1 要解决的是「**买得放心、愿意再买、运营看得见、后台管得住**」。因此本版本的排期逻辑不是按功能列表顺序，而是按**四条主线**归并：

| 主线 | 要解决的问题 | 主要功能 |
|------|--------------|----------|
| ① 信任线 | 商品页没有评价，转化缺背书 | F01 评价晒单、E01 商品属性（让商品信息可信、可筛） |
| ② 履约线 | 发货只有状态变更，用户不知道货在哪 | E02 订单中心、E03 物流管理、F07 轨迹查询 |
| ③ 留存线 | 无券无积分无收藏，复购无抓手 | F06 优惠券满减、F05 收藏足迹、F09 积分、F02 消息通知 |
| ④ 管控线 | 后台报表浅、账号权限写死、录入效率低 | F03 报表、F04 账号权限、F08 装修、F11 批量导入、E06 库存盘点 |

### 1.2 排期原则
| 原则 | 说明 |
|------|------|
| **先还债再盖楼** | V1.0 遗留的 4 个缺口（见 §1.3）必须先修，否则新功能建在断路上 |
| **闭环优先** | 每个阶段结束时，主线上的链路必须端到端可演示（不能只交半条） |
| **高风险前置** | 优惠券的金额分摊改造提前设计评审，不等开工才想 |
| **兼容不破坏** | 属性改造、用券改造都必须保证存量数据与在途订单不受影响 |
| **测试随功能走** | 新功能同步补 Pest + Vitest 用例，不留到最后一期集中补 |
| **文档同步** | 表结构/接口变更即时更新 `CubeShop_Database_Design_v1.1`、`CubeShop_API_v1.1` |

### 1.3 一期开工前必须处理的 4 个存量缺口（代码核对结论）

| # | 缺口 | 为什么必须前置 |
|---|------|----------------|
| 1 | 订单无「确认收货」入口（无接口、无自动确认任务），`shipped → completed` 走不通 | **直接阻塞 F01 评价**（评价要求已完成订单）；且所有已在途订单都受影响 |
| 2 | 后台发货接口只收 `remark`，不录快递公司/单号，无 `shippings` 表 | 阻塞整条履约线（E03/F07），也影响订单导出 |
| 3 | 后端改密接口 `POST /auth/password` 已实现，web 端无个人中心页 | 功能闲置；且「收藏/足迹/优惠券/积分」入口都无处挂载 |
| 4 | 后台 SKU 规格靠纯文本手输 + 硬编码维度 key | 商品数据债，越晚迁移成本越高；E01 改造必须先做数据迁移脚本 |

### 1.4 技术基线（延续 V1.0，V1.1 增量）
- 后端：Laravel 13 + PostgreSQL + Redis（队列/缓存，邮件与导出走队列）（如果没redis，走postgresql）+ Sanctum + spatie/permission
- 前端：Vue 3 + TS + Vite + Tailwind（web 用户端 / admin 管理端）
- 新增外部组件（三期引入）：Meilisearch（单二进制，Docker Compose 加一个服务）
- 第三方服务（二期申请）：快递轨迹查询渠道（快递100 / 快递鸟）、SMTP 邮件通道

## 2. 阶段总览

| 阶段 | 名称 | 主线 | 目标 | 建议周期 | 预估人天 |
|------|------|------|------|----------|----------|
| V1.1-P1 | 一期：打通信任与管控（含还债） | ①④ | 订单走到终点、商品属性化、评价上线、后台管得住 | 2.5~3 周 | 12~15 |
| V1.1-P2 | 二期：打通营销与履约 | ②③ | 能发券能核销、能看物流轨迹、首页可运营 | 2.5~3.5 周 | 10~14 |
| V1.1-P3 | 三期：效率与增长 | ③④ | 积分留存、搜索提速、录入提效、盘点留痕 | 2~2.5 周 | 10~12 |
| V1.1-P4 | 收尾：回归、压测与发布 | — | 全链路回归、并发压测、上线 | 0.5~1 周 | 3~4 |

> 周期口径：1 名后端 + 1 名前端 + 0.5 名测试并行。单人全栈串行则约为上述总和的 1.6~1.8 倍。
> 总计约 **7.5~9.5 周**（含收尾），累计 35~45 人天。

```
V1.1-P1 一期 ──► V1.1-P2 二期 ──► V1.1-P3 三期 ──► V1.1-P4 收尾发布
 还债+信任+管控      营销+履约          效率+增长         回归+压测+上线
```

## 4. 阶段依赖关系

```
V1.1-P1 一期
 ├─ S0 前置：E02-A 确认收货 ──► F01 评价（强依赖）
 ├─ E05-A 个人中心页 ──► F05 收藏 / F02 通知 / （二期）F06 我的券 / （三期）F09 积分 挂载点
 ├─ E01 属性/SPU ──► 前台规格置灰、属性筛选 ──►（二期）E03 按重量计费、（三期）F10 索引字段
 └─ F03 报表 / F04 账号权限（独立，无外部依赖）

V1.1-P2 二期
 ├─ F06 优惠券 ──► 依赖 P1 的报表口径（核销统计）与订单金额链路
 ├─ E03 物流改造 ──► F07 轨迹展示（先后关系，E03 先）
 ├─ E03 按重量计费 ──► 依赖 P1 的 products.weight
 └─ F08 首页装修（独立，可并行）

V1.1-P3 三期
 ├─ F09 积分 ──► 依赖 P1 的 E02 确认收货（入账时点）与 F06 金额明细（抵扣口径）
 ├─ F10 搜索 ──► 依赖 P1 的 E01 属性字段（筛选维度入索引）
 ├─ F11 导入 ──► 依赖 P1 的 E01 属性模型（导入字段含属性）
 └─ E06 盘点 / E07 异步导出（独立，可并行）

V1.1-P4 收尾 ──► 依赖全部阶段
```

**关键路径**：`E02-A 确认收货 → F01 评价 → F06 用券金额改造 → F09 积分抵扣`。这条链上任何一环延期都会连带影响后续，建议全程专人跟进。

**可并行项**：F03 报表 ∥ F04 账号权限 ∥ E07 通用体验（一期）；F08 装修 ∥ E03 物流（二期）。

## 6. 风险与应对

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| 确认收货改造影响在途订单（一刀切自动确认） | 用户投诉 / 数据错乱 | 中 | 自动确认天数可配置；上线前先跑历史数据统计；先灰度限制为「新发货订单」再全量 |
| E01 属性改造破坏存量商品数据 | 在售商品无法下单 | 中 | specs JSONB 读取路径完全保留；迁移脚本先出校对清单人工确认；灰度开关控制新表单；上线前做全量数据演练 |
| 优惠券金额分摊与退款耦合出错 | 资损 | 中高 | 规则先评审定稿；订单冗余分摊快照；按行项目退款；上线前做「券+满减+退款」组合矩阵测试与并发压测 |
| 物流第三方渠道资质/额度受限 | 二期延期 | 中 | 先交付「手填单号 + 前端展示」降级方案；渠道账号并行申请；适配器模式便于换渠道 |
| Meilisearch 引入新运维组件 | 部署复杂度上升 | 低 | 单二进制 Docker Compose 部署；索引可随时重建；搜索异常时回退数据库查询（保留开关） |
| 积分规则反复变更 | 三期返工 | 中 | 规则先定稿再开工；参数全部走 `system_configs`，避免硬编码 |
| 邮局/邮件通道不可用 | 通知触达失败 | 低 | 站内信为兜底主通道；邮件队列失败重试 3 次，失败可后台补发 |
| 需求蔓延（做成了 V1.2 的内容） | 版本延期 | 高 | 严格按本文档范围执行，新需求进 V1.2 备忘清单，不在本版本插队 |
