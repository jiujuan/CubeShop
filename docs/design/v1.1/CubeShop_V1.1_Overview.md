## 1. 规划背景

### 1.1 V1.0 现状盘点
V1.0 已交付「浏览 → 加购 → 下单 → 支付 → 后台发货」完整交易闭环：

| 模块 | 已有能力 |
|------|----------|
| 商品 | 分类（两级）、商品/SKU/多图、上下架、搜索（关键词+价格区间）、销量/价格/时间排序 |
| 交易 | 购物车、库存锁定（事务+流水+防超卖）、订单状态机、超时自动取消 |
| 支付 | 微信/支付宝沙箱、回调验签+幂等、金额校验、退款申请与审核 |
| 运营 | 仪表盘概览、订单发货、退款处理、订单导出、操作日志、系统配置、库存预警 |
| 质量 | Pest 111 用例（SQLite + PG 双库全绿）、Vitest 前端用例、每日 PG 回归自动化 |

### 1.2 V1.0 的主要短板（V1.1 的机会点）
1. **无复购钩子**：没有优惠券、积分、会员等任何营销与留存手段，拉新后留不住。
2. **无信任背书**：商品详情页没有评价/晒单，转化率缺少关键支撑。
3. **履约体验断层**：发货后用户看不到物流轨迹，订单详情到「已发货」就断头。
4. **运营深度不足**：仪表盘只有 4 个数字，没有趋势、排行、占比等经营分析；首页无运营位，改版需改代码。
5. **后台账号管理缺位**：角色/权限靠种子数据写死，后台没有管理员账号管理页，加人需改数据库。
6. **搜索是 LIKE**：商品量上去后关键词搜索体验与性能都会恶化。

## 2. V1.1 目标与范围原则

### 2.1 版本目标
> **一句话**：在稳固 V1.0 交易闭环的基础上，补齐「信任（评价）、留存（营销）、履约（物流）、经营（报表）、管控（后台账号）」五大短板。

- 交易闭环不动：核心下单/支付/库存逻辑只做扩展（如用券），不重构。
- 每个功能都要有明确的后端支撑设计（表/接口），不允许纯前端假功能。
- 沿用 V1.0 质量基线：新功能必须带 Pest + Vitest 用例，PG 兼容性回归持续跑。

### 2.2 范围原则
- **纳入**：路线图 §7 预告的 7 项能力 + 后台账号权限管理 + 首页运营位（均为单体架构内可承载的功能）。
- **不纳入（留待 V1.2）**：多商户/店铺体系、秒杀/拼团、分销、App/小程序端、国际化、微服务化。

### 3.1 存量功能增强清单（E 系列）

除上述新增功能外，V1.1 还要把 V1.0 已有功能做深。明细见 [CubeShop_V1.1_Enhancement.md](./CubeShop_V1.1_Enhancement.md)。

| 编号 | 增强项 | 端 | 优先级 | 分期 | 说明 |
|------|--------|----|--------|------|------|
| E01 | 商品属性与 SPU/SKU 规格体系 | 双端 | P0 | 一期 | 属性库 + 分类属性模板 + 笛卡尔积生成 SKU；治掉「规格文本手输」数据债 |
| E02 | 订单中心增强 | 双端 | P0 | 一期 | **确认收货闭环（前置修复）**、状态时间轴、列表分组检索、再次购买 |
| E03 | 物流管理存量改造 | 双端 | P1 | 二期 | 发货接口升级（必填单号）、快递公司字典、批量发货、冗余单号、运费模板 |
| E04 | 用户地址管理增强 | 双端 | P1 | 一期 | 省市区级联、地址标签、智能粘贴解析、常用度排序、结算页内联新增 |
| E05 | 账号与安全增强 | 用户端 | P0 | 一期 | **补齐个人中心页**（改密接口已存在但前端无入口）、改密强度与撤销其他设备 Token、登录设备、换绑 |
| E06 | 库存与商品运营增强 | 后台 | P2 | 三期 | 库存盘点单、批量调价、商品变更留痕、预警阈值分级 |
| E07 | 后台通用体验增强 | 后台 | P1 | 随各期 | 筛选记忆、列偏好、顶栏快捷搜索、批量操作条、导出异步化 |

> **四条必须优先处理的存量缺口（核对代码后确认）**：
> 1. 订单 `shipped → completed` 无入口（无确认收货接口、无自动确认任务）→ **直接阻塞 F01 评价**，一期首日修；
> 2. 后台发货只收 `remark`，不录快递单号 → 阻塞 F07 物流；
> 3. 修改密码后端已实现、前端无个人中心入口 → 功能闲置；
> 4. 后台 SKU 规格为纯文本手输（硬编码维度 key）→ 数据债，越晚迁移越贵。

## 4. 分期计划（V1.1 内部三阶段）

> 本节为概要视图。**权威排期、阶段任务清单、依赖关系与里程碑见 [CubeShop_Roadmap_v1.1.md](./CubeShop_Roadmap_v1.1.md)**。

### 一期（信任与管控，预计 12~15 人天）
范围：**E02 确认收货闭环（首日前置）**、E01 商品属性与 SPU、E05 个人中心与改密、F01 评价晒单、F02 消息通知、F03 报表增强、F04 账号管理、F05 收藏足迹、E04 地址增强、E07 通用体验。
特点：无外部第三方依赖（邮件用现有 SMTP 配置），风险低、见效快；E01 是本版本最大单体工作量（含老数据迁移）。

### 二期（营销与履约，预计 10~14 人天）
范围：F06 优惠券满减、F07 物流轨迹 + E03 物流存量改造、F08 首页装修、E05-C/D 登录设备与换绑。
特点：优惠券涉及订单金额计算改造（下单/退款链路）与库存式发券，是本版本最高风险项；物流需申请第三方服务（快递100/快递鸟）账号。

### 三期（效率与体验，预计 10~12 人天）
范围：F09 积分、F10 搜索引擎、F11 批量导入、E06 库存盘点与批量调价、E05-E 账号注销。
特点：可选外部组件（Meilisearch 单二进制部署成本低），积分规则需产品先定稿。

```
一期（信任/管控/数据债）──► 二期（营销/履约）──► 三期（效率/体验）
 E02-A 确认收货（前置）      F06（高风险前置联调）   F09
 E01 属性/SPU  E05 账号      F07 + E03 物流          F10  F11  E06
 F01 F02 F03 F04 F05         F08  E05-C/D            E05-E
 E04  E07
```

> E01 的数据迁移脚本与 E02-A 的确认收货闭环建议在正式开工前单独评审；前者涉及存量商品数据，后者一刀切影响所有在途订单。

## 5. 关键风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| **订单无法流转到 completed（存量缺口）** | F01 评价功能无法验收 | 一期首日交付确认收货接口 + 自动确认任务（E02-A），并在验收清单中列为前置项 |
| **E01 属性改造涉及存量商品数据** | 迁移出错影响在售商品 | 保留 specs JSONB 读取路径不破坏兼容；迁移脚本先出校对清单人工确认；灰度开关控制新表单启用 |
| 优惠券与订单金额计算耦合，退款分摊复杂 | 资损 / 状态错乱 | 一期即输出用券金额分摊规则设计并评审；订单表冗余优惠明细快照；退款按行项目分摊 |
| 物流第三方服务选型与资质 | 二期延期 | 先做「后台手填单号 + 前端展示」的降级方案，轨迹 API 后补 |
| 评价内容合规（违禁词/刷评） | 合规风险 | 评价先审后显可配置；后台提供屏蔽/回复能力；敏感词过滤接入 |
| 邮件/短信通道不可用 | 通知触达失败 | 站内信为兜底主通道，邮件异步队列发送失败重试 |
| 功能蔓延超出 V1.1 范围 | 版本延期 | 严格按本清单排期，新增需求进 V1.2 备忘 |

## 8. 术语约定（V1.1 用户表拆分后生效）

> 权威说明见 [CubeShop_UserTable_Split_Analysis.md](../CubeShop_UserTable_Split_Analysis.md) 第八节。

| 术语 | 指向 | 表 / 模型 |
|---|---|---|
| **用户**、**买家** | 前台注册的购买者 | `users` / `App\Models\User` |
| **账号**、**后台账号**、**管理员** | 后台运营与超级管理员 | `sys_user` / `App\Models\SysUser` |

对应后台模块：**用户管理**管买家（`/admin/users`），**账号管理**管管理员（`/admin/accounts`）。
买家不参与 spatie 权限体系，`customer` 角色已移除。
