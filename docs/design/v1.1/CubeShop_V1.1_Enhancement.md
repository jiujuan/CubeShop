## 0. V1.0 现状核对结论（先看这个）

逐项核对代码后的实测结论，**其中 4 项是必须先补的缺口**：

| # | 现状事实 | 判定 | 影响 |
|---|----------|------|------|
| 1 | `Order::TRANSITIONS` 允许 `shipped → completed`，但**没有用户确认收货接口，也没有自动确认收货任务** | ⚠️ P0 缺口 | 订单发货后永久停在「已发货」，永远无法进入「已完成」→ 直接阻塞 F01 评价功能（要求已完成订单） |
| 2 | 后台发货接口 `POST /admin/orders/{id}/ship` **只接收 `remark`**，不录快递公司/单号；无 `shippings` 表 | ⚠️ P0 缺口 | 物流功能无从谈起，导出也无法带单号 |
| 3 | 后端 `POST /auth/password`（修改密码）**已实现**，但 web 前端**没有个人中心页面**（`/account` 下只有收货地址） | ⚠️ P1 缺口 | 改密接口完全闲置，用户无法自助改密码 |
| 4 | 后台 SKU 规格是**纯文本手输**：`ProductEditView` 用硬编码 key 数组 `['颜色','尺码','规格','容量','轴体','版本']` 按位置切分成 JSONB | ⚠️ P1 数据债 | 无法加自定义维度、无法复用、前台只能从 SKU 反推维度；越晚迁移成本越高 |
| 5 | 前台 `DetailView` 已能从 SKU 提取规格维度并匹配 SKU，但**没有可选性联动**（选中红色后，不存在的「S 码」仍可点，只提示"请选择完整规格"） | 可优化 | 体验毛刺 |
| 6 | `products` 无品牌、无商品参数、无重量；无属性库/规格模板；无属性筛选 | 增强 | 商品模型偏薄 |
| 7 | `user_addresses` 字段齐全（省市区+详址+默认），前后台 CRUD 已通（含后台代改） | 基本达标 | 缺标签、地区级联、智能解析 |

## E01 商品属性与 SPU/SKU 规格体系（P0 · 一期，本版本最重要的存量改造）

### 现状问题
- **规格录入靠文本约定**：后台表单一行填「黑色/M」，后端按固定 key 顺序硬塞进 `specs` JSONB。想加一个「长度」维度做不到；换一个类目（如耳机）就要改代码里的 key 数组。
- **没有属性库**：同一件商品在不同商品里重复手输「黑色」，拼写不一致就会分裂成两个值，无法统计与筛选。
- **没有商品参数**：材质、功率、尺寸这类不参与销售、只用于展示和筛选的信息无处存放（`description` 是富文本，无法结构化）。
- **没有品牌**：无品牌字典，无法做品牌筛选与品牌馆。
- **无重量**：运费只能整单固定，无法做按重量/按地区计费。

### 增强方案（标准 SPU/SKU 模型）

**新增数据模型**
| 表 | 作用 |
|----|------|
| `brands` | 品牌字典（名称、logo、排序、启用） |
| `attributes` | 属性库：`name`（颜色）、`type`（spec=规格属性 / param=参数属性）、`is_filterable`（是否前台可筛选）、`is_multiple`（是否多值） |
| `attribute_values` | 属性可选值：`attribute_id`、`value`（白/黑/S/M/L）、`sort` |
| `category_attributes` | 分类 ↔ 属性模板：该类目下的商品必须/可填哪些属性，决定后台表单动态渲染 |
| `product_attribute_values` | 商品参数值（含多值场景） |
| `products` 增字段 | `brand_id`、`weight`（克）、`video_url`、`keywords`（搜索补充词） |

**后台改造（ProductEditView 重构为核心工作量）**
1. 选择分类后，自动按 `category_attributes` 渲染属性表单（规格属性 + 参数属性分区展示）。
2. 规格属性：为每个属性勾选可选值（来自 `attribute_values`，支持表单内快捷新增）。
3. **一键生成 SKU 表**：按勾选的规格值做笛卡尔积生成 SKU 行（如 颜色 3 × 尺码 4 = 12 行），支持：
   - 按维度批量设值（「所有 M 码 +5 元」）；
   - 批量填充库存、SKU 编码自动编号（商品编号-序号）；
   - 行级启用/禁用，删除某组合。
4. 参数属性：直接填值，展示到前台参数表。
5. SKU 表格保留「纯文本模式」开关作为逃生舱（批量粘贴导入）。

**前台改造**
- 详情页规格选择器升级：**不可选值置灰**（无该组合或组合库存为 0），价格/库存/主图随选择联动，全部选中但无货时提示「该规格暂时缺货」。
- 新增「商品参数」表格（品牌、分类、以及全部参数属性）。
- 列表/搜索页新增**按属性筛选**（可筛属性的值多选，如「材质：304 不锈钢」）。

**兼容与迁移**
- 老商品 `specs` JSONB 结构保持不变，读取路径不改，仍可正常展示与下单。
- 提供一次性迁移脚本：扫描现有 `products.specs` 的 key/value，反推注册到 `attributes`/`attribute_values`，并建立分类属性模板；结果生成校对清单，人工确认后再启用新表单（避免自动猜测污染属性库）。

### 验收标准
- 新建三分维度规格商品，SKU 行数 = 各维度值数量的笛卡尔积，无遗漏。
- 前台选中「黑色」后，不存在的尺码置灰不可点；选齐后价格/库存/图片正确联动。
- 属性筛选结果与实际商品属性一致；下架商品不出现在筛选结果。
- 老商品（迁移前创建）可正常浏览、加购、下单，无回归。
- 按重量计费的商品运费计算正确（若同版本开通运费模板）。

### 预估
后端 5 天 / 后台前端 4 天 / 前台前端 2.5 天（本版本最大单体工作量）

## E02 订单中心增强（P0 · 一期，前置修复 + 体验补全）

### 现状问题
1. **订单走不到终点**：无确认收货接口、无自动确认收货任务 → 阻塞评价功能。
2. 订单列表只能按状态筛选：无订单号搜索、无时间区间、无「待收货/待评价」分组。
3. 订单详情信息偏薄：有 `paid_at/shipped_at` 字段但缺少可视化时间轴；无物流信息（见 E03）。
4. 无「再次购买」；用户复购要重新走搜索 → 详情 → 加购。
5. 无商家侧订单备注、无订单状态变更流水（`sys_operation_log` 是后台操作视角，不是订单视角）。

### 增强方案

**A. 确认收货闭环（前置修复，最高优先）**
- 新增 `POST /api/storefront/orders/{id}/confirm`：`shipped → completed`，校验订单归属 + 状态，幂等（重复调用返回成功不重复写入），写 `completed_at`。
- 新增 Command `orders:auto-complete`：每小时执行，发货后超过 N 天（`system_configs` 新增 `order.auto_complete_days`，默认 7）自动确认收货，并在订单日志中标记「系统自动确认」。
- 用户端订单详情：已发货状态展示「确认收货」主按钮 + 「物流查询」（E03）。

**B. 订单详情：状态时间轴**
- 竖向时间轴：下单 → 支付成功 → 已发货 → 已完成，每节点显示时间；未到达节点置灰；取消/退款走异常分支展示。
- 关联动作区：复制订单号、发票信息（可选）、申请退款、评价（F01 联动）、再次购买。

**C. 订单列表：分组与检索**
- Tab 分组：全部 / 待付款（含倒计时） / 待发货 / 待收货 / 待评价（已完成未评价） / 退款售后。
- 检索：订单号、收货人姓名/手机号、下单时间区间。
- 列表卡片信息增强：商品缩略图组、件数、实付金额、状态标签、可用操作按钮（去支付/取消/确认收货/申请退款/评价/再次购买）。

**D. 再次购买**
- `POST /api/storefront/orders/{id}/rebuy`：按行项目批量加购；下架或无库存的行跳过，返回「已加入 N 件，M 件不可购买（含原因）」，前端跳购物车并提示。

**E. 后台订单增强**
- 订单详情新增：状态流转记录（`order_logs` 表：from/to/操作人/原因/时间，可选）、商家备注（多行、仅后台可见）、客户信息（历史订单数、累计消费）。
- 订单列表新增：发货超时预警、物流异常标记（E03）、订单来源/设备（可选）。
- 导出扩展：增加快递公司、运单号、确认收货时间列。

### 验收标准
- 发货 → 用户确认收货 → 状态 = completed → 详情页出现评价入口，全链路可演示。
- 超期订单被自动确认，日志有记录且幂等（重复执行不重复写入）。
- 「再次购买」部分失效商品场景提示准确，购物车数量正确。
- 订单号/收货人搜索与时间区间筛选结果准确。

### 预估
后端 2.5 天 / 前端 3 天

## E03 物流管理（P1 · 二期）—— 与 F07 合并，本文档只列 V1.0 存量改造点

V1.0 的发货只是一次状态变更，V1.1 要把它变成「有单号、有轨迹、可批量」的完整履约链路。设计见 [Backend_Design §1.2 / §2](./CubeShop_V1.1_Backend_Design.md)，此处补充改造清单：

| # | 改造点 | 说明 |
|---|--------|------|
| 1 | 新增 `express_companies` 字典表 | 编码、名称、查询渠道 code、启用、排序；后台可维护 |
| 2 | `POST /admin/orders/{id}/ship` 升级 | body 由 `{remark}` 变为 `{express_company_code, tracking_no, remark?}`；单号必填 + 格式校验（去空格、长度 8~32，字母数字横线） |
| 3 | `orders` 冗余字段 | `express_company` / `tracking_no` 冗余存储，便于列表展示、导出、筛选 |
| 4 | 批量发货 | `POST /admin/orders/batch-ship`：Excel 导入（order_no + company_code + tracking_no），返回逐行校验结果 |
| 5 | 物流异常看板（可选） | 后台聚合：发货 > 48h 无轨迹、轨迹停滞 > 72h、签收失败，列表可跳转处理 |
| 6 | 用户端物流卡片 | 订单详情展示快递公司 + 单号 + 复制按钮 + 轨迹时间线（倒序）；第三方接口异常时降级为「单号 + 官方查询外链」，不白屏 |
| 7 | 运费模板（可选，与 E01 重量字段配套） | `freight_templates`：按地区/按重量首重续重计费，替代当前固定运费；无模板时退回固定运费 |

**验收**：发货必填单号；用户端 1 分钟内可见物流卡片；批量发货 100 单 1 分钟内完成且失败行有明确原因；导出含单号列。

## E04 用户地址管理增强（P1 · 一期）

### 现状
`user_addresses` 字段齐全，用户端 CRUD + 默认地址、后台代改（V1.0 刚交付，含脱敏与快照不可变校验）均已通过测试。属于「基本达标、但离好用还有距离」。

### 增强方案
| # | 增强项 | 说明 |
|---|--------|------|
| 1 | **省市区三级级联** | 内置行政区划数据（`regions` 表或打包 JSON），选择器替代手输；同时保留手输逃生（兼容港澳台及海外地址，行政区划数据需按国家规范口径） |
| 2 | **地址标签** | 家/公司/学校 + 自定义（≤4 字）；列表与选择器展示标签 |
| 3 | **智能粘贴解析** | 粘贴一行文本自动拆分姓名/手机/省市区/详址（前端正则 + 后端校验兜底） |
| 4 | **默认地址一致性** | 删除默认地址后自动把剩余最新一条设为默认，并提示用户；无地址时结算页给明确空态引导 |
| 5 | **使用频次排序** | `user_addresses` 增 `used_count` / `last_used_at`，下单时计数，地址列表按常用度排序 |
| 6 | **结算页内联新增** | 结算页可直接新增地址（弹窗），不跳出结算流程，成功后自动选中 |
| 7 | 上限与权限一致性（V1.0 已有 20 条上限） | 级联选择器上线后复查校验路径，避免新字段绕过既有校验 |

**验收**：级联选择与手输双通道都能保存成功；删除默认地址后必有默认或明确空态；结算页内联新增后自动选中并可下单。

**预估**：后端 1.5 天 / 前端 2 天

## E05 账号与安全增强（P0 · 一期）

### 现状问题
- 后端已有 `POST /auth/password`（修改密码）、`GET/PUT /user/profile`（资料）、`POST /user/upload`（头像），但**web 前端只做了登录/注册/地址页，没有个人中心**，这三个接口在前台完全闲置。
- 需核对项（开发前确认）：改密是否校验旧密码、是否有强度校验、改密后其他设备 Token 是否仍有效（大概率有效，Sanctum 默认不撤销）。

### 增强方案
**A. 个人中心页（新页面 `/account`）**
- 资料卡：头像上传、昵称、手机号/邮箱（脱敏展示 + 换绑入口）、注册时间。
- 安全卡：修改密码、登录设备管理、退出全部设备。
- 订单快捷入口：全部订单 / 待付款 / 待收货 / 待评价（跳订单列表 Tab）。
- 其他入口：收货地址、我的优惠券（F06）、积分（F09）、收藏（F05）、足迹（F05）。

**B. 修改密码强化**
- 校验：旧密码必填校验 + 新密码强度规则（8~20 位，需含字母与数字，规则可配置在 `system_configs`）+ 确认密码一致 + 新旧密码不同。
- 改密成功后**撤销其他设备 Token**：只保留当前请求的 Token（Sanctum 按当前 token id 精确删除其余），前端提示「其他 N 台设备已退出登录」。
- 触发通知：站内信 + 邮件（复用 F02 通知服务）告知密码已变更，若非本人操作可申诉。

**C. 登录设备管理（P1）**
- `GET /me/sessions`：列出有效 Token（设备名/最后活跃时间/IP 归属地近似）；`DELETE /me/sessions/{id}` 单独踢出。
- 需 `personal_access_tokens` 增加 `device_name` 展示与活跃时间维护（Laravel 已有 `last_used_at`）。

**D. 换绑手机/邮箱（P1）**
- 验证码校验原值 + 新值；换绑后同样发通知。

**E. 账号注销（P2 · 三期）**
- 提交注销申请 → 7 天冷静期（期间登录可撤销）→ 到期执行匿名化处理；未完成订单/未退款项时禁止提交。

**验收**：改密后其他设备 Token 立即 401（Pest 用例覆盖）；弱密码被拒且有明确提示；设备列表可踢出指定设备；错误旧密码不泄露任何策略信息。

**预估**：后端 2 天 / 前端 2.5 天

## E06 库存与商品运营增强（P2 · 三期）

| 增强项 | 说明 |
|--------|------|
| 库存盘点单 | `inventory_checks` + `inventory_check_items`：录入实盘数 → 自动算差异 → 审核后调整库存并写 `inventory_logs`（差异原因必填），全程留痕 |
| 批量调价 / 批量上下架 | 基于现有 `/admin/products/batch` 扩展：按分类或筛选条件批量改价（支持按比例/按固定额） |

| 库存预警升级 | 阈值支持按商品覆盖全局默认；预警走通知中心（F02）推给运营角色 |
| 低库存自动下架（可选） | 配置开关，库存为 0 时自动置为下架并记录原因 |
